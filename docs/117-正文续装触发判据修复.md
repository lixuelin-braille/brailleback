# 117 - 正文续装触发判据修复

> 日期：2026-11-26
> 分支：`fix/reader-append-window`，基线 `4fd7487`
> 对应缺陷：[114-待修-正文续装不触发](./114-待修-正文续装不触发.md)；诊断取证见 [116-阅读器滚屏卡顿诊断](./116-阅读器滚屏卡顿诊断.md) §6「续装专项」。
> 本轮是真改：116 只记录不修，本轮把续装判据换成基于实际可见窗口的口径，补纯函数表驱动单测，模拟器跑到文末并核对页码、计数与 UI 树。

## 1. 根因

### 1.1 源码事实（改动前口径，`4fd7487`）

- `compose/ReaderBodyList.kt`：正文是一段一项的 `LazyColumn`，`itemsIndexed(segments, key = { index, _ -> index })`；滚动监听挂在 `LaunchedEffect(segmentCount)` 的 `snapshotFlow { listState.firstVisibleItemIndex }.distinctUntilChanged()` 上。
- 旧续装判据在 collect 内：`index >= listState.layoutInfo.totalItemsCount - 4` 才回调 `onNeedMoreSegments()`。判据看的是**首可见项下标**。
- `ReaderPageNavigator.kt` 的 `onNeedMoreSegments()`：`next = mWindowEndUnit + 1`，`next >= totalUnits()` 早返；否则 `mWindowSegments = mWindowSegments + buildUnitSegments(next, readingUnit())`，只往后**追加**段落，不替换 `focusSegments`，也不动 `scrollToken`。
- 项 / 页换算：`WINDOW_PAGES = 3`，初始窗口铺当前页 + 后两页；一个 unit（页）在窗口里折成若干段。实测本书 41 页 / 150 段，初始窗口 14 段，覆盖 unit 0、1、2（unit0 段 0–3、unit1 段 4–7、unit2 段 8–13）。旧判据卡死时正停在 unit 2，所以 41 页的书只走到第 3 页。

### 1.2 实测事实（r1 根因探针，`verify/fix/raw/r1/logcat.txt`）

同一本 `perf_base.txt`（150 段 / 41 页 / 16 行），从第 1 页连续上滑，停住那一刻的埋点读数：

| 量 | 值 |
|---|---|
| `totalItemsCount` | 14 |
| 视口可见项数 `visibleItemsInfo.size` | 5（个别帧 6） |
| 首可见项下标 `firstVisibleItemIndex` | 9 |
| 末可见项下标 `lastVisibleItemIndex` | 13 |
| 旧阈值 `totalItemsCount - 4` | 10 |
| 旧判据比较 | `9 >= 10` → **false**，`onNeedMoreSegments()` 一次未进 |
| 续装事件 / `scrollToken` 递增 / `showPage` 整窗重铺 | 0 / 0 / 0 |

### 1.3 换算链（为什么差 1 项，且物理上不可达）

1. LazyColumn 一屏能摆 `V` 项；首可见项下标的物理上限是 `total − V`（最后一项贴屏底时，首项只能露到 `total − V`）。
2. 实测 `V = 5`，`total = 14`，首可见上限 `14 − 5 = 9`。
3. 旧阈值要求首可见下标 `>= total − 4 = 10`。`9 < 10`，**只要视口可见项数 `V > 4`，这个阈值在列表边界就不可能被踩到**——不是滑动没滑到位，是判据本身不可达。
4. 旁证：末可见项此时已经是 `13 = total − 1`，即窗口尾部早就到了；旧判据却只认首项，看不到末项。
5. 旧代码在别的字号 / 屏幕下偶尔能过，条件是可见项数 `V ≤ 4`（此时首项上限 `total − V ≥ total − 4`，阈值可达）；18sp、1080×2340 / 440dpi 这台机器上一屏摆 5 项，必然卡死。

结论：根因不是 `itemsIndexed` 项数与 `totalItemsCount` 语义不一致，也不是追加后 recomposition 没刷新，而是**判据选错了锚点**——用首可见下标去够一个随视口项数浮动的阈值，视口项数一多阈值即不可达。

## 2. 改法

### 2.1 判据换成可见窗口口径（首选方案）

`ReaderBodyList.kt` 抽出两个无副作用的纯函数 / 纯守卫，供 Composable 与单测共用：

- `shouldAppendMore(lastVisibleIndex, totalItemsCount, trailingSlots = 2)`：末可见项距列表末尾 `≤ trailingSlots` 项即应续装；空列表 / 非法下标返回 false。判据看**末可见项**，距离末尾多远与视口摆几项无关。
- `AppendGate`：续装去重守卫。
  - `canAppend(last, total)`：过 `shouldAppendMore`，且同一 `total` 还没续过装才放行；
  - `noteAppended(total)`：记下本次追加前的 total，进入待命；
  - `observeTotal(total)`：观察到 total 真正变大（段落已落进 state）才清掉待命标记；
  - `isSettled()` / `canProbeEnd(total)`：待命落定后仍贴在末尾，才再向 Activity 发一次**文末探测**，走溢出 / 到头播报分支，不重复追加。

collect 入口从「首可见单项快照」改为三元组快照 `AppendScrollState(firstIndex, lastIndex, total)`，`distinctUntilChanged` 去重后：先 `onTopSegment(firstIndex)` 跟页号，再交守卫判定。

### 2.2 文末到头播报

`ReaderPageNavigator.onNeedMoreSegments()` 的 `next >= totalUnits()` 分支：此前直接 `return`；本轮在该分支补到头播报——`mAnnouncedEnd` 守卫同一文末不重复刷，记 `page overflow: 到文末 unit=… total=…` 日志，并 `announce(getString(R.string.braille_reader_at_end))`。`onTopSegment` 退回倒数第二页之前（`unit < totalUnits() - 2`）才复位 `mAnnouncedEnd`；贴在末尾的两页之间不重复播报。

续装路径保持原样：只追加 `mWindowSegments`，不替换 `focusSegments`，不递增 `scrollToken`，不回顶。

### 2.3 被否掉的改法

- **每帧轮询**（`LaunchedEffect` 里 `while + delay` 反复读 `layoutInfo`）：被红线禁止；会跟滑动抢帧，且 `snapshotFlow` 本就是对列表状态变化的响应式订阅，不需要轮询。
- **第二套滚动监听**：在 `onTopSegment` 之外再叠一套滚动回调 / 状态机判续装；两条路径会各自维护一份「是否贴末尾」的状态，容易打架。
- **改成「最后一页已可见即续装」**（次选）：语义上与新判据接近，但落点仍是末可见项判定；本轮直接用末可见项距末尾槽位的距离做判据，槽位可调，覆盖「贴末尾前预留一页余量」的场景。
- 未采用「按首可见项 + 把槽位改成随可见项数动态算」：那样判据仍绑死视口布局，换字号 / 屏幕还要再调；末可见项口径天然与可见项数解耦。

### 3.6 翻译前沿不误报（补边界）

**现象**：到头播报挂在 `onNeedMoreSegments()` 的 `next >= totalUnits()` 分支。对正在翻译的长书，`totalUnits()` 只是当前已翻出并落进流的页数，会随 `appendBrailleStream()` 持续增长；读者快速滑到翻译前沿时，`next` 可能 ≥ 当时的 `totalUnits()`，旧代码不看翻译状态会直接播「已经是书的末尾了。」，而后面还有页面陆续译出。150 段小书翻译已完成，上一轮测不出这条边界。

**取证（大书 `big2_book.txt`，4500 段 / 1,001,489 字节）**：

- f6：40 滑 / 300ms；f7：250 滑 / 120ms（快速连续滑）。两轮末尾分支探针 `diag-endbranch` 进入 **0 次**，`page overflow` 误报 **0 次**。
- f7 终态：读者 `unit=362 / 全书 1216 units`；最后一次 append `append: +50384 stream=852105->902489 cells=897990 units=1216 pos=51254`；`translate end: paragraphs=4500 chars=902490 invalidCells=0 failedAt=0 elapsed=19322ms`、`translate done: paragraphs=4500 failedAt=0 units=1216`。
- 本轮 f9：开大书后立即爆发 150 滑 / 120ms；翻译中 `append: units=1200→2350→3319→4355→4500`，`translate end elapsed=8517ms`、`translate done: paragraphs=4500 failedAt=0 units=4500`；翻完那一刻读者约 `unit=53`，爆发终态 `unit=885 / 4500`；`overflow=0`。
- **为什么模拟器测不到误报**：模拟器翻译约每 2 秒 publish 一块（f7 每块约 +110～120 units），滑动每滑仅推进约 0.35 unit，翻译始终跑在读者前面，`next < totalUnits()` 恒成立，末尾分支根本不进。
- **代码层面可达条件（源码事实，非理论推测）**：当读者节奏 > 翻译 publish 节奏（慢真机、超长段落、翻译服务繁忙），读者 top unit ≈ `totalUnits−1` 时，`mWindowEndUnit = min(currentUnit+2, totalUnits−1) = totalUnits−1`，于是 `next = mWindowEndUnit+1 = totalUnits`，进入末尾分支；旧代码无条件播报。

**守卫做法（真实信号，不用固定延时猜结束）**：

- 复用翻译生命周期已有状态位 `mTranslating`：`startTranslation()` 置 `true`；`applyTranslatedChunk()` 的 `chunk.done` 分支（含失败停在部分译文）、首段失败回退、isFinishing 分支置 `false`。
- 抽出纯函数 `canAnnounceBookEnd(translating, alreadyAnnounced)`：`!translating && !alreadyAnnounced`。末尾分支播报前过该谓词；翻译进行中即使进入末尾分支也不播报、不置位；翻完（含部分译文停下）后再滑到文末才播一次。
- 顺带修掉同一文末重复播报：复位标记原来只看 `unit < totalUnits()-2`，前进贴末尾的几页之间也会被复位，导致重复播报。改为纯函数 `shouldReenableEndAnnounce(newUnit, oldUnit, totalUnits)`：**只有往回退**（`newUnit < oldUnit`）且退到倒数第二页之前才复位；前进贴末尾不复位。
- `setBrailleStream()` 进入新内容时复位 `mAnnouncedEnd`，避免上一本的标记压住新书真正的文末播报。
- 未采用：`totalUnits()` 变大时复位标记（只是缓解、会留一次误报）；固定延时猜「翻译大概结束」；每帧轮询翻译状态。

**回归（f8 小书 / f9 大书翻译中 / f10 大书翻译后）**：

| 场景 | 到头播报 | 日志原文 |
|---|---|---|
| f8 小书 150 段（翻译已完成）滑到文末 | **1 次** | `page overflow: 到文末 unit=145 total=150` |
| f9 大书翻译中滑到前沿 | **0 次** | 无 `overflow`；`translate done: paragraphs=4500 failedAt=0 units=4500` |
| f10 大书 `translate done` 后滑到末尾 | **1 次** | `page overflow: 到文末 unit=4494 total=4500` |

- 纯滑动窗：`scrollToken` 递增 **0**、`showPage` 整窗重铺 **0**；续装只走 `scroll window` 追加路径，不替换已有项、不回顶。
- 文案仍取 `R.string.braille_reader_at_end`（zh-rCN「已经是书的末尾了。」），未改资源与播报语义。
