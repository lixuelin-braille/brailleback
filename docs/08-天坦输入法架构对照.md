# 天坦输入法 8.2.8 架构对照

抓取方式：`adb pull` 手机上的 `com.tatans.inputmethod`（versionCode 73 / targetSdk 33 / 41.5 MB），
jadx 反编译到 `.tmp-tatans-ime\src\sources`，清单用 aapt2 导出到 `.tmp-tatans-ime\manifest.txt`。
以下每条都标了可核对的类或行号，不是推测。

## 一、它的身份结构：一个纯输入法，没有无障碍服务

清单里只有三类对外组件，没有 `BIND_ACCESSIBILITY_SERVICE`：

- `net.tatans.inputmethod.TatansIme`（`BIND_INPUT_METHOD`，`manifest.txt:255-267`）
- `net.tatans.inputmethod.ImeOpeService`（导出，action `tatans.open.intent.action.IME_SERVICE`，`:249-254`）
- `net.tatans.inputmethod.providers.ImeOpenProvider`（导出，写权限 `net.tatans.inputmethod.permission.WRITE_IME_STATE`，`:274-278`）

`ImeOpeService` 持有 `IScreenReaderController controller`，对外提供 `speak(String,int,int)`、
`performClick(List<String>)`、`interruptFeedback()`、`setTouchExplorePassThrough(Rect)`、
`requestTouchExploration(boolean)`、`onInputModeChanged(boolean)`
（`ImeOpeService.java:42-92`）。也就是：**播报、点击、触摸探索全部外包给外部读屏**，输入法自己不当读屏。

`AccessibilityMonitor` 只读不申请：用 `AccessibilityManager` 加 `TouchExplorationStateChangeListener`，
再查 `isSoundBackEnabled` / `isTalkManEnabled` 判断"现在哪个读屏在跑"
（`utils\AccessibilityMonitor.java:14-62`）。

## 二、它的盲文链路：点位 → 拼音 → 商业引擎

`com.dwengine.hw.BrailleCore`：

- `inputPoints` 存点位串，`"0"` 作音节分隔，上屏前 `"0"` 换成 `'`（`BrailleCore.java:57-60`）
- 每按一格：整串点位交 `BrailleToPinyin.parse()` 转拼音，然后 `tatansIMECore.reset()` + 把拼音逐字符重放
  （`BrailleCore.java:295-303`）。**候选是整体重建的**，靠 `selectIndex` 只在本轮有效
- `BrailleToPinyin` 是**代码内硬编码的点位→拼音表**（`pointsPy`），并实现 `g/k/h` 与 `j/q/x`、
  以 `i/ü` 开头韵母时的改写规则，`SPECIAL = 1235/12345/12356/123456/13456`
  （`BrailleToPinyin.java:16-18`，表在 `:230` 一带逐条 `map.put`）
- 候选真正来自原生引擎：`libDWIMECore.so`（2.1 MB）+ `assets/enterprise/py.data`（12.43 MB 拼音词库）
  + `md.data`（6.81 MB），`cell_ext.data` 0.43 MB。`TatansIMECore` 的
  `getEngineCandString` / `selectEngineCand` / `getEngineCommitString` 都是 JNI 调用
- **候选分池**：`brailleCandStart = 3`（`BrailleCore.java:37`）。前 3 个槽位留给引擎高频词，
  第 3 个之后才插盲文侧自己的特殊候选（"哦"/"哟"，见 `getCandString`/`isSpecialCandidates`）
- 盲文侧候选上屏时先让引擎出字再替换：`selectEngineCand(0)` → 取 `getEngineCommitString()` → 换成盲文文本
  （`BrailleCore.java:118-130`）

## 三、它没有点显器硬件支持

整个反编译产物里没有 `UsbManager` / `UsbDevice` / `BluetoothSocket` / `点显` 任一处命中。
它的"盲文键盘"是纯屏幕布局：`KeyboardType.KEYBOARD_BRAILLE`（四列按键，
`keyboard\BrailleKeyboardLayout.java`）与 `KEYBOARD_HALF_BRAILLE`（半方，用地三四五六点组合键，
`keyboard\HalfBrailleKeyboardLayout.java:173-185` 里 `"六点"／"四六点"／"五六点"` 的 contentDescription）。

## 五、对照表

| 维度 | 天坦输入法 8.2.8 | 本项目（林夕 / brailleback） |
| --- | --- | --- |
| 无障碍服务 | 无，纯 IME | `BrailleBackService`（点显器必须） |
| 与读屏协作 | AIDL `ImeOpeService` 把播报/点击/触摸外包给读屏 | 自己是读屏的子模块，`BrailleIme.initialize` 由服务调用 |
| 点显器硬件 | 不支持（无 USB/蓝牙代码） | 支持（CP210x USB + RFCOMM SCN5） |
| 屏幕盲文键盘 | 六点 + 半方两种布局 | TalkBack 移植件（单 IME，形态由 `pref_single_ime_view_mode` 决定） |
| 点位→拼音 | 代码内硬编码表 + gkh/jqx、i/ü 规则 | `cell_pinyin.txt` 1302 条（ctb 反推）+ `SyllableSplitter` |
| 候选来源 | 商业引擎 `libDWIMECore.so` + 12.4 MB 词库 | 自建 `pinyin_index.txt` 25,967 串 / 36,144 条 + 字频与常用字表 |
| 重算方式 | 每格 `reset()` 引擎 + 重放整串拼音 | 整串重切分 + 把已选文本绑定到格区间 |
| 选字模型 | 引擎候选优先，`brailleCandStart=3` 分池 | 词候选窗口 1–3 音节，同池按词频排序 |

## 六、可借鉴的四点

1. **"输入法调读屏"而不是"输入法内置读屏"**——`ImeOpeService` 这套桥，正好解掉"没有无障碍服务就没有语音"
   的死结：独立 IME 形态下用 AIDL 找已装的读屏（天坦、保益、TalkBack）替自己播报候选。
   本项目对应改动点：`BrailleIME` 在 `getHost() == null`（`talkBackForBrailleIme` 未被注入）时走一条
   `ScreenReaderBridge`，只做 `speak` 一件事，其余保持沉默。

2. **候选分池**——把"词候选"固定占前几个槽位、"单字候选"后置，并在播报时分段说明
   （"前 3 个是词，第 4 个起是单字"）。盲人靠听编号选字，混排会乱。
   本项目改动点：`CandidateCursor` 增加 `poolStart` 概念，`describeCandidates` 分两段播。

3. **硬件键盘就出输入区**——`configuration.keyboard == 2` 是最廉价可靠的判据。
   本项目可以把现在的 `displayConnected` 改成 `displayConnected || config.keyboard == 2`：
   蓝牙点显器不算 HID 键盘，但 USB HID 小键盘、笔记本自带键盘、OTG 键盘都算，覆盖更宽。

4. **不要学它的重算方式**——每按一格 `reset()` 引擎再把整串拼音重放，候选整体重建，
   用户换过的候选必然丢（它只能靠一次性的 `selectIndex`）。本项目绑定格区间的做法是对的，
   别为了"跟专业输入法一样"退回去。

## 七、结论

天坦输入法的"简单"来自**把语言学部分外包给商业引擎**（12.4 MB 词库 + JNI），
所以它能用一套很粗的点位→拼音转换就撑起体验；它的"轻"来自**不当无障碍服务**，
靠 AIDL 借读屏的嘴和手。

本项目走的是相反路线：语言学部分自建（已经做出 34.9 万词反查的拼音索引），
但硬件通道绑死在无障碍服务里。两边各缺一块，能互相补的正是这两块。

## 八、点显器其实不依赖无障碍（已落地）

对照天坦之后又核了一遍自家代码，结论是**硬件通道本来就可以脱离无障碍**：

- 点显器连接在 `service/.../display/DisplayService.kt`，是普通 `Service` + `IBrailleService`
  绑定（`android:permission=PERMISSION_CONNECT`、`exported=false`），**不是无障碍服务**。
  `onBind` 里直接 `autoConnectBraille()`（`:537-541`）。
- 无障碍服务没开时，连接靠 `promoteDisplayForeground()` 把服务提升为
  `connectedDevice` 前台服务保活（`DisplayForegroundKeepAlive.kt`），这正是"不开无障碍也能连"的原因。
- 输入事件是**广播给所有客户端**的（`DisplayService.broadcastInputEvent`：`beginBroadcast` 遍历
  `mClients`），所以输入法只要自己当客户端就能收到点位按键。
- `DisplayClient`（`client/.../DisplayClient.kt`）是纯客户端封装，同应用可直接 `new`，
  自带重连（最多 5 次、500 ms 退避）。

据此新增 `ime/ImeDisplayBridge.kt`：没有宿主时由输入法自己 `DisplayClient` 连点显器，
`onInputEvent` → `BrailleIME.onHardwareInputEvent`，显示宽度取 `displayProperties.numTextCells`，
点位回显自己写第一格、1.5 秒后清屏。

**唯一的红线是双处理**：`broadcastInputEvent` 会发给每个客户端，无障碍服务在跑时两套同时活着，
一个按键会被处理两遍。因此：
- 只在 `getHost() == null` 时建立连接；
- 每次 `onStartInputView` 重新对齐（`reconcileImeDisplay`），宿主出现就立刻 `stop()`；
- `onInputEvent` 里再判一次 `hostActive()`，宁可丢一次也不重复上屏。
