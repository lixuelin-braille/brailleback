## 一、断连恢复

### 1. 半开 RFCOMM 链路无传输超时，读循环永久挂起，不触发断连回调与自动重连

**现象与证据**

- 蓝牙读循环直接在阻塞流上 `read`，全程没有给 socket 设置读取超时：
  - `service/src/main/java/com/googlecode/eyesfree/braille/service/display/ReadThread.kt:27` 字段 `mSocket: BluetoothSocket?`；
  - `ReadThread.kt:106` 取局部引用 `val socket = mSocket ?: return`；
  - `ReadThread.kt:112` `socket.inputStream.read(buf, 0, buf.size)` 阻塞等待；
  - `ReadThread.kt:122-129` 只有读到流尾（`-1`）退出循环，或抛 `IOException` 被 `:127-129` 捕获后退出；
  - 全文件检索不到 `setSoTimeout` / `SO_TIMEOUT` / 心跳看门狗。
- 断连回调只在 `cleanup()` 里发出：`ReadThread.kt:217-225`，其中 `ReadThread.kt:223` 调 `mDisplayService.onDisplayDisconnected()`。
- 自动重连只在收到断连/失败回调后才调度：`DisplayService.kt:665-667` → `DisplayServiceHandler.kt:80`；退避重连入口 `DisplayServiceConnectionFlow.kt:267-291`，其前提是链路已被判定断开。USB 失败路径同理：`DisplayServiceListeners.kt:108`。
- 即：只要 `read()` 不返回，`cleanup()` 不跑，`onDisplayDisconnected()` 不发，退避重连链路整条不会启动。

**真实影响（盲人用户视角）**

点显器中途没电、休眠、离开蓝牙范围，或耳机/路由器抢频导致 RFCOMM 链路进入半开状态时，对端已经不再发数据，但手机侧的 socket 没有报错。界面仍显示「已连接」，点显器却不再出点；用户翻页、查菜单全都没有反馈，只能手动拔插设备、重开蓝牙或重启 App，属于典型的「设备还在、输出死了」。

**修复成本**：M（2–4 天）。方向：给蓝牙 socket 设读取超时（如 30–60 秒一档），`read` 超时累计 N 次无数据即判定链路死亡，走既有 `closeSocket()` → `cleanup()` 路径，接入现有退避重连；或在驱动线程侧加独立心跳看门狗。USB HID 路径已有 `HidConnectionLifecycle` 看门狗，蓝牙路径缺对应物。

**是否阻塞发布**：否。这是既有现象，不是本轮提交引入；但属于真机高优先修复项，半开链路在日常使用中高发。

> 交叉引用：现象层面「有线点显器几十秒后停更、应用层无传输超时」已在 [34-线程与Handler盘点](./34-线程与Handler盘点.md) 登记；本条补到具体代码位置与改法方向。

## 二、盲文输出正确性

### 2. 拼音索引异常捕获面不全，加载失败后本次进程内永久不再重试

**现象与证据**

- 索引单例在 `getInstance` 里只捕 `IOException` 与 `RuntimeException`：`addon/braillecommon/src/main/java/com/google/android/accessibility/braille/common/translate/PinyinIndex.kt:153-161`；`OutOfMemoryError`、`SecurityException` 等 `Error` 子类不在捕获面内。
- 失败后置位 `loadFailed`：`PinyinIndex.kt:127`；此后 `getInstance` 在 `PinyinIndex.kt:133-137` 直接返回 `null`，进程存活期间不再读 assets、不再重试。
- 服务预热处同样只捕 `RuntimeException`：`brailleback/src/main/java/com/googlecode/eyesfree/brailleback/BrailleBackService.kt:574-578`，预热抛出的 `Error` 会漏出 `onCreate`。
- 索引来源：`service/src/main/assets/pinyin_index.txt`（641,595 字节），读取与 gz 兼容分支在 `PinyinIndex.kt:229-237`。

**真实影响（盲人用户视角）**

两种后果：其一，若索引解析/打开资源抛出未被兜住的异常，无障碍服务 `onCreate` 直接崩，手机读屏整体起不来；其二，若异常被兜住，本次进程内候选永远退回单字路径，同音字排序与「点位串→词」失效，用户打同一个拼音只能翻单字候选，直到杀掉进程重启。

**修复成本**：S（≤1 天）。方向：`getInstance` 的 catch 放宽到 `Throwable`（至少补 `OutOfMemoryError`、`SecurityException`）；确认 `loadFailed` 不跨进程持久化（当前是内存标志，冷启动即重置，核对无 SharedPreferences 残留即可）；`BrailleBackService.kt:574-578` 预热处同步补 `Error` 兜底，保证索引失败不拖垮服务主链路。

**是否阻塞发布**：否。当前 assets 实测可正常解析；属于异常路径防护缺口。

#### 观察项（速览表未单列）：AutoValue `annotationProcessor` 与 Kotlin 混编的构建顺序依赖

**现象与证据**

- addon 主源码有意保留的 6 个 Java 文件：接口 `TalkBackSpeaker.java`、桩 `EditBufferStub.java`、三个 AutoValue 类（`BrailleInputOptions.java:23` `@AutoValue`、生成类引用见 `:35`；`BrailleDisplayForBrailleIme.java`、`TranslationResult.java`）、JNI 桥 `LouisTranslation.java`。

**是否阻塞发布**：否。

### 4. 单字字频同字重复条目被低频覆盖（latent，当前数据未触发）

**现象与证据**

- 建索引时单字条目直接覆盖写字频：`PinyinIndex.kt:198-200`，赋值在 `:199` `charFrequencies[text[0]] = frequency`，不取最大值。
- 条目在 `PinyinIndex.kt:203` 按词频降序排序，因此同一字出现多次时，后写入的是低频值。
- 实测当前 `pinyin_index.txt` 无重复单字条目（0 条），今天不会触发；属于随数据再生埋下来的隐患。

**真实影响（盲人用户视角）**

一旦再生词库让同一个字在多条单字条目里出现，字频会被低频覆盖成「低优先」，同音字排序把低频字排到高频字前面，候选首选字判错，盲人首键上屏的就是错字。

**修复成本**：S（≤1 天）。方向：`PinyinIndex.kt:198-200` 改为取 `max`（已存在频率与新频率的较大值），与词频表口径对齐。

**是否阻塞发布**：否。

### 5. 点位回显整屏清零；两份实现常量未收口，内容到达未取消回显

**现象与证据**

- 回显实现已拆到独立文件：`brailleback/src/main/java/com/googlecode/eyesfree/brailleback/DisplayPressEcho.kt`（commit `72e8fee`）。
- 回显帧构造时把整屏点位置零、只填第 0 格：`DisplayPressEcho.kt:54-59`；超时 1500ms 后 `restore()` 调 `refresh()` 还原：`DisplayPressEcho.kt:60-62`、`DisplayPressEcho.kt:67`。
- 独立输入法侧存在同构实现：`ImeDisplayBridge.kt:93-107`，同样整屏构造零帧、同样 1500ms 常量（`ImeDisplayBridge.kt:51`），两份实现各写一份常量。
- `DisplayManager.kt:828-829` 是唯一入口 `showPressedDots`；新正文到达的内容路径上没有调用 `pressEcho.cancel()`（`cancel()` 只在作用域销毁时随 `displayScope.cancel()` 一起走，`DisplayManager.kt:283`）。

**真实影响（盲人用户视角）**

打字间隙如果阅读流刷新、候选刷新到达，回显帧会把正文压掉 1.5 秒：点显器上只看到当前按下的那一个点位，其余位置空白；松开手后才还原。连续打字场景下表现为正文「一闪一闪被清屏」。

**修复成本**：S（≤1 天）。方向：内容刷新路径到达时调用 `DisplayPressEcho.cancel()` 取消待还原定时器；或回显改为掩码叠加——只在当前格覆盖点位，不清零其余格。两份实现（`DisplayPressEcho.kt` / `ImeDisplayBridge.kt`）的 1500ms 常量应收口到同一处。

**是否阻塞发布**：否。回显残留、自连侧清屏语义不一致、光标错位、双客户端竞态、窄屏截断等风险已在 [57-点位回显与输入法自连链路](./57-点位回显与输入法自连链路.md) R1/R3/R4/R7 逐条展开，其阻塞判定以该文为准；本条只登记「常量双份 + 内容路径未取消回显」这一结构债。

## 三、TalkBack 朗读语义

### 6. 宿主在跑时仍无条件初始化系统 TTS 兜底引擎

**现象与证据**

- 输入法创建即注册兜底并预热 TTS：`brailleback/src/main/java/com/googlecode/eyesfree/brailleback/BrailleIME.kt:202-203`，`setFallbackSpeaker(...)` 后直接 `ImeSpeech.warmUp(this)`。
- `warmUp` 冷启动 `TextToSpeech` 实例：`brailleback/src/main/java/com/googlecode/eyesfree/brailleback/ime/ImeSpeech.kt:53-96`；引擎在 `BrailleIME.onDestroy` 关闭：`BrailleIME.kt:218-225` → `ImeSpeech.kt:99-110`。
- 宿主模式下桥非空，播报走桥、不碰兜底：`addon/braillecommon/.../BrailleCommonTalkBackSpeaker.kt:67-78`，但 TTS 引擎已被 `warmUp` 提前建好并常驻。

**真实影响（盲人用户视角）**

读屏在跑时，兜底 TTS 永远不会被调用，却多占一个 TTS 引擎实例与内存；少数机型上两个引擎同时持有语音焦点，可能出现宿主播报被兜底引擎抢打断的边角问题。

**修复成本**：S（≤1 天）。方向：`warmUp` 延迟到第一次 `fallback.speak` 真正被调用时再初始化（懒加载）；或在 `reconcileImeDisplay` 判定 `hostPresent` 时跳过预热（`BrailleIME.kt:297-313`）。

**是否阻塞发布**：否。兜底与系统读屏重复播报、语音抢话的成因与阻塞判定见 [57-点位回显与输入法自连链路](./57-点位回显与输入法自连链路.md) R5；本条只登记「宿主在跑仍常驻一个空转 TTS 引擎」这一资源债。

### 9. 源码契约测试与行为测试混在同一 `src/test`，全绿无法区分「行为正确」与「字面未改」

**现象与证据**

- 五个真实测试目录：`brailleback/src/test`（58 文件）、`service/src/test`（28 文件）、`addon/braillecommon/src/test`（6）、`addon/brailleime/src/test`（1）、`brailleback/src/androidTest`（6）。
- 其中 25 个 `*ContractTest.kt` 靠读源码文本做静态断言：`brailleback/src/test` 19 个、`service/src/test` 6 个；另有 3 个非 `ContractTest` 命名的同类静态扫描测试：`BrailleCodeCatalogTest.kt`、`SingleImeRegistrationTest.kt`、`VersionCatalogTest.kt`。代表：`DisplaySplitContractTest.kt:31-33`（`srcText()` 直接 `readText()` 断言子串）、`DisplaySplitContractTest.kt:66-75`（`walkTopDown()` 扫整棵源码树找旧写法）、`NativeBridgeContractTest.kt:72-146`（断言 Java/Kotlin 方法名集合与 C 侧 JNI 符号一一对应）。
- 同目录下是真实行为测试：`RefreshGateTest.kt`、`WordWrapStrategyTest.kt`、`DisplayContentTest.kt`、`BrailleFileDecoderTest.kt`、`HeadingRulesTest.kt` 等，跑的是类实例与数据。
- 路径解析依赖测试运行目录：`DisplaySplitContractTest.kt:21-29` 用 `File(repoRelativePath)` / `File("..", ...)` / `File("../..", ...)` 三候选探测；换工作目录时直接 `error("找不到 ...")`，不是跳过。

**真实影响（盲人用户视角）**

测试全绿时维护者无法判断：是行为真的对，还是源码字面没被契约钉住。两类失真：其一，行为回归只要保留了原字面写法就漏网；其二，保持行为的改名、抽函数、挪文件会误红，逼测试跟着改字面。混放还意味着一份测试报告同时承担「结构守护」与「行为验证」两种职责，出问题时定位成本高。

**修复成本**：M（2–4 天）。方向：目录或包名上分 `contract` 与 `behavior` 两组（不必拆 module）；契约测试在类注释里标注「钉结构不钉行为」清单；cwd 探测改为向上回溯找 `settings.gradle` 定位仓库根，去掉三候选相对路径。逐文件归类、三档分层（L1 行为 / L2 资源与 ABI 契约 / L3 结构护栏）与 CI 补跑缺口见 [56-测试分层与源码契约测试整改](./56-测试分层与源码契约测试整改.md) 全文，本条不重复其处置表。

**是否阻塞发布**：否。

### 10. addon 单测仍为 Java，跨语言签名漂移只在编译期暴露

**现象与证据**

- addon 主源码已 Kotlin 化（193 kt），但测试仍有 7 个 `.java`：`addon/braillecommon/src/test` 6 个、`addon/brailleime/src/test` 1 个；`service/src/test` 另有 7 个 Java 行为测试（`BluetoothDiscoveryPolicyTest.java`、`BondedDeviceFilterTest.java`、`HidConnectionLifecycleTest.java`、`HidInputReportNormalizerTest.java`、`UsbBrailleDeviceTest.java`、`WujieBrailleFrameCodecTest.java`、`WujieKeyEventCodecTest.java`）。
- Java 测试经 Kotlin 编译产物调用 addon 的 Kotlin 公开签名；Kotlin 改了方法名/参数可空性后，Java 侧在编译期才报错，单测运行期不参与签名协商。

**真实影响（盲人用户视角）**

无直接运行期故障；风险是签名演进时编译告警分散在混编边界，容易漏看一处，导致某条输入/播报路径在真机上才暴露调用不到。

**修复成本**：S（≤1 天/批次）。方向：择机把 7 个测试翻成 Kotlin；过渡期在跨语言调用点保留编译告警，纳入 lint 观察。测试清单与「先纳入 CI 门禁、再谈语言跟迁」的优先级见 [55-addon与client-Kotlin化迁移复盘](./55-addon与client-Kotlin化迁移复盘.md) §1.3/R5。

**是否阻塞发布**：否。
