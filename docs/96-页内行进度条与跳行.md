# 96 · 页内行进度条与「跳到本页第 N 行」

## 用户诉求

> 每一页都可以有个进度条滑块，进度条可以显示本页有多少行，点击进度条可以弹出数字输入法，
> 比如可以输入第 10 行，设备就跳转到第 10 行，这样，滑动进度条的时候可以一行一行的拖动这种效果。
>
> 希望这两个焦点合并（「第 19 行 / 共 19 行」按钮，条滑块）成一个。

读屏用户先说清了两件事：**页码管整本书**，**行进度条管这一页**；而
「第 N 行 / 共 M 行」的文字按钮和滑块条在 TalkBack 下曾是**两个焦点**——读完行号要跳一次、
调滑轨又要跳一次，来回找位置。所以最终形态是「一个焦点、两种操作」。

## 行是什么

这里的「行」= **屏幕排版的一行**（`mCellsPerLine` 方，竖屏约 45 方），不是点显器的一屏（30 方）。
理由与 95 号文档一致：屏幕按普通电子书排页，点显器只从 `mOffset` 独立推送，
不为了对齐点显器去改阅读单位。代价是一行在点显器上大约 1.5 屏，行内继续靠点显器自己的逐行键走。

行起点必须与 `screenAt()` 的折行规则**完全一致**，否则「第 10 行」跳过去会落在两行之间。
于是折行逻辑抽成 `BrailleFileDecoder.lineStarts()`：

```kotlin
fun lineStarts(
    stream: String,
    offset: Int,
    cellsPerLine: Int,
    maxLines: Int,
    endLimit: Int = stream.length,
): IntArray
```

逐行推：段内按 `cellsPerLine - 回行缩进` 折、段边界换行、行尾用 `wrapEnd()` 回退到词边界
（93 号「不劈字」的规则），碰到 `\n` 就跳到下一段，`endLimit` 保证不越过本页终点。

Activity 在 `showPage()` 里算一次并存进 `mPageLineStarts`，页面其他字段都从它派生：

- `uiState.lineCount = mPageLineStarts.size`
- `uiState.lineIndex = mPageLineStarts.indexOfLast { it <= mOffset }`（当前行）

## 跳行

```kotlin
private fun moveToPageLine(index: Int) {
    val i = index.coerceIn(0, mPageLineStarts.size - 1)
    val target = mPageLineStarts[i]
    if (target == mOffset) return
    mOffset = target
    sendToDisplay()   // 点显器也跟着走
    showPage()        // 屏幕重绘 + 刷新行号
    saveProgress()
}
```

只在本页范围内动，不跨页：进度条说的就是「这一页有几行」，拖到底等于本页最后一行。

点「第 N 行」文字（触摸）或 TalkBack 双击 → `showPageLineDialog()` → `ReaderDialog.PageLine`
→ `NumberInputDialog`（纯数字输入，提示 `1 - 本页行数`）→ `onPageLineConfirmed(n)` → `moveToPageLine(n - 1)`。
用户说的是「第 10 行」，所以输入从 1 开始，内部 0 基。

## 一个焦点（无障碍）

这一块**只能有一个无障碍节点**，踩过两次坑才定下来：

1. 行信息文字与 M3 `Slider` 并排 → 页码一处、行号一处、滑块一处，TalkBack 连停三次。
2. 用 `mergeDescendants` 把整块并起来、把行号 `Text` 用 `clearAndSetSemantics` 清空
   → 树里仍然是 `SeekBar` 父节点 + 一个带描述的 `View` 子节点，读屏把「滑块」读两遍。
   根因：M3 `Slider` 自带 `progressBarRangeInfo`/`setProgress` 语义，与我们在外层声明的
   描述各自成节点，合并语义压不平。
3. 把描述挂到 `Slider` 上、文字 `invisibleToUser()` → 依旧是 `SeekBar` 父 + 描述子两个节点。

最终做法：**不用 M3 Slider，自己画**（`LineScrubber`）。
一个 `Box`，`Canvas` 只画像素（文字用 `rememberTextMeasurer` + `drawText`，滑轨与圆点用
`drawLine`/`drawCircle`），语义整块声明一次：

```kotlin
Box(
    Modifier.fillMaxWidth()
        .height(barHeight)                 // 页码小字 + 行信息 + 滑轨
        .pointerInput(lineCount, maxIndex) { /* 按下即跳到该行，横拖跟手 */ }
        .semantics {
            contentDescription = description        // 只有 "第 4 行 / 共 21 行"
            progressBarRangeInfo = ProgressBarRangeInfo(...)   // 上下滑一格一行
            setProgress { onSeek(...); true }
            onClick(label = "输入行号") { onEdit(); true }      // 双击弹数字输入
        }
) { Canvas(...) }
```

子节点为零 → 树里只有一个 `SeekBar` 节点，描述只有行信息。页码改成滑轨上方一行
小字**只画在屏上**（`onSurfaceVariant`，比正文字号小 4sp），不进朗读内容——
用户明确要求「滑块里不需要页码信息」。要听页码时可用「跳页」按钮的对话框。

## 实测

设备 24117RK2CC（Android 17，竖屏，`mCellsPerLine = 45`，`mLinesPerPage = 21`）：

- 页表 `page table: unit=945 pages=…`，本页 21 行。
- 点滑轨 1/2 处、靠右、靠左：`page line: -> 10 offset=2513 -> 2251`、
  `-> 17 offset=2251 -> 2513`、`-> 3 offset=2513 -> 1993`（点显器同屏推送、进度保存）。
- `uiautomator dump` 全屏 34 个节点，这块只有**一个**：
  `android.widget.SeekBar content-desc="第 6 行 / 共 20 行"`（`bounds=[45,1555][1035,1751]`），
  没有子节点、没有第二个「滑块」、描述里没有页码。
- 单测 `BrailleWordWrapTest` 新增两例：`lineStarts` 行数必须等于 `screenAt` 渲染的行数
  （`cells = 3..12`、`maxLines = 1..8` 全组合），每行起点递增且落在词边界（除超长词）；
  另一例验证不越过 `endLimit`。

## 朗读只有行号，没有百分比

`progressBarRangeInfo` 一挂上，TalkBack 调滑块时默认念「百分之多少」。行号才是这里的读数，
百分比对书页没有意义，所以同一节点上再声明 `stateDescription = description`：

```kotlin
stateDescription = description      // "第 6 行 / 共 20 行"
```

`stateDescription` 会覆盖系统对 SeekBar 的百分比播报，且不影响上下滑的调节行为。

## 未决

- 行 = 屏幕一行（45 方），点显器一屏 30 方：用户对「第 10 行」的直觉若按点显器屏算，需要再确认；
  当前按屏幕排版走，与「像正常电子书」的既定方针一致。
- TalkBack 上下滑是否按 `steps` 精确一格一行，需用户在真机上用读屏实际操作确认手感，
  adb 无法模拟 TalkBack 的焦点手势。
