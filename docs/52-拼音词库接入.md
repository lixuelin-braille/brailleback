# 52 · 拼音词库接入（离线索引已产出）

> 目标：让「几个音节」直接出**词**候选，而不是逐字选。只解决候选来源与排序，不改动分词（分写）逻辑。

## 一、结论

词库早就在仓库里（`service/src/main/assets/jiebadt.txt`，34.9 万词带词频），**缺的是「拼音 → 词」这一面的索引**。已用一次性离线脚本把这一面建出来，产物已放进 assets：

- `service/src/main/assets/pinyin_index.txt` — 627 KB **明文**（打包时 aapt 会把 `.gz` 解开并去掉后缀，所以入库就是明文，见文末「坑」），25,967 个拼音串，36,144 条词/字
- 格式：每行 `去调拼音串 \t 词:词频,词:词频,...`，按 key 升序（可直接二分，也可整体载入）
- 口径：拼音去调、`ü → v`；只有 `词频 ≥ 100` 的入库；单字条目保留（5,029 条），可当**字频表**用

## 二、构建数据（`jiebadt.txt` 34.9 万条）

| 指标 | 数值 |
|---|---|
| 词条总数 | 349,046 |
| 成功转拼音 | 348,973（99.98%） |
| 含非汉字跳过 | 72 |

词级拼音来自 pypinyin 的 `phrases_dict.json`（47,111 条），所以多音字按词定音："银行" → `yinhang`，不会变成 `yinxing`。

## 三、真实语料上的收益（项目 docs 里 74,959 汉字）

| 指标 | 数值 |
|---|---|

| 两字能命中词库 | 36,704（63.8%） |
| 命中时只有 1 个候选 | 20,583（占命中的 56%） |

即：**两字输入里约 64% 可以一次成词，其中一半以上一次上屏、不用选字。** 逐字选字的量随之大幅下降。

## 四、运行时怎么用

1. 首次用到时 `GZIPInputStream` 解析进 `HashMap<String, List<Entry>>`，36k 条，内存约 4–6 MB、耗时 50–100 ms，可放在输入法第一次上屏前预热；
2. 查词：把「未确认的音节序列」拼成去调拼音串，从最长（3 音节）到最短（1 音节）依次查；
3. 合成候选：词优先、单字兜底；同层级按 `词频` 排序；用户选过的词加权；
4. 声调仍然有用：词库无调，我们的输入有调，可用声调在候选里过滤，减少同音词。

## 五、接进输入侧还必须改的事

1. **pending 范围**：`SyllableSplitter` 现在只让「最后一个音节」待确认（`held.start > lastConfirmedStart && candidates.size() > 1`）。词跨 2–3 音节，必须把待确认范围放宽到「未确认的词」；
2. **跨格消费**：选中一个词要一次吃掉 2–3 个音节对应的格，`appendSpace`/`commit` 的确认逻辑要跟着改；
3. **候选条**：屏幕上要能显示词候选（第 3 项需求的候选视图），否则词的收益只能靠报读；
4. **降级**：`pinyin_index.txt.gz` 缺失或解析失败时，退回现在的单字候选路径。

## 六、已知限制

- 词频来自 jieba 通用语料，不贴盲文用户表达习惯，需用户选词学习来补；
- 同调同音词只能靠词频："一声/医生/一生" 全是 `yi1sheng1`，`yisheng` 的第一候选是"一声"（16017），医学语境会错；
- 三字以上词（成语、专名）命中率低（本次语料 3 字窗口仅 1.3%），先不投入；
- 72 条含字母/数字的词（如 `γ射线`）没进索引，走单字兜底。

## 七、脚本

- `.tmp-pinyin-index/build.py` — 覆盖率统计与截断代价对比
- `.tmp-pinyin-index/build_asset.py` — 生成 assets 资源并回读验证（改 `THR` 可调词频阈值）
- `.tmp-pinyin-index/coverage.py` — 真实语料命中率

词频阈值取舍（gzip 体积）：thr=0 → 2.9 MB / thr=100 → 322 KB / thr=300 → 158 KB / thr=1000 → 65 KB。当前取 100。

## 八、运行时已接通的部分（2026-11-21）

- 资源：`assets/pinyin_index.txt`（627 KB 明文）+ `assets/cell_pinyin.txt`（20 KB 明文）。
  **坑**：`.gz` 结尾的 asset 在打包时会被 aapt 自动解压并**去掉 `.gz` 后缀**，运行时按 `pinyin_index.txt.gz` 打开必然 `FileNotFoundException`。现已改成按明文名读，并在 `PinyinIndex.openAsset` 保留对 `.gz` 的兜底。
- `PinyinIndex.java`：字频（5,029 字）、点位串→拼音（1,302 条）、拼音串→词（25,967 串 / 36,144 条）。
- 预热：`BrailleBackService.onCreate` 调用一次。实测日志 `I/BBPinyin: ready in 278ms: words=25967 chars=5029 cells=1302`。
- 已生效：`ChineseBrailleTableIndex` 的候选排序改成「有词频的字按词频降序 → 616 字常用表 → GB2312 一级字 → 生僻字」，同音字不再是表内顺序。
- 未生效：词候选。`PinyinIndex.wordsFor*` 已可用，但 `SyllableSplitter` 的 pending 仍只认最后一个音节，词跨音节装不进去，要等下一步改造。

## 九、词候选（已接通）

`SyllableSplitter` 的尾部从「压 1 个音节」改成「压最多 3 个音节的窗口」：

1. 每来一个新音节，若窗口已有 3 个，最旧的那个按自己的候选落定（它已经不可能出现在尾部 3 音节里）；
2. 循环结束时，从最长（3 音节）往短查词库，命中就把整组当一个候选组，`pendingStart` 指向词的首格；
3. 词候选只认「贴着尾部」的组合：更前面的音节早已落定，回头改写会让已念过的字在输入框里跳变；
4. 组之前的音节先落定；词唯一解或已确认过时，整组按词落定，**不会**退化成一个音节一个字地拼；
5. 词库/拼音表缺失、音节查不到拼音时，行为与接入前完全一致（只留最后一个音节）。

实测（`docs` 语料 7.5 万汉字）：两字窗口 63.8% 能命中词库，其中 56% 只有 1 个候选。

**已知限制（下一步要补）**：用户若在待确认的词上**换过候选**（比如把「计算机」换成别的），然后继续打下一格，重新切分时这个词会被按单字重算，之前换过的候选序号会套到单字候选上，可能蹦出一个不对的字。修法是把「已选定的词」绑到起始格下标上（`CandidateCursor` 记 `start → (词文本, 音节数)`），重新切分时先按绑定输出再跳过对应音节。未选定就继续打的场景不受影响——那时词里每个字本来就是首选字，产出的文本一样。
