# 17 - 保活与权限适配（含 Android 17 行为变更）

> 生成日期：2026-11-15
> 触发问题：真机上「点显器不动了」没有原因可查，服务被系统或厂商省电策略杀掉时是**静默断开**的。
> 对应提交：`StabilityLogic.kt` / `compose/StabilityComposeActivity.kt` / `compose/StabilityScreen.kt` / `res/xml/settings.xml` 新增入口。

## 为什么需要这一屏

无障碍服务被回收时，用户侧唯一的现象是「点显器不动了」，与「点显器没连上」「翻译卡住」「屏幕内容没变」无法区分。
这一屏把四件会影响进程存活的事摊开显示，并给出一键入口：

| 项 | 判定 | 不达标的处理动作 |
|---|---|---|
| 前台服务是否在跑 | `BrailleBackService.getActiveInstance() != null` | 先去无障碍里启用（未启用时「没在跑」是正常状态） |
| 电池优化白名单 | `PowerManager.isIgnoringBatteryOptimizations(pkg)` | `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 系统确认框 |
| 厂商后台限制 | `ActivityManager.isBackgroundRestricted` | 跳厂商自启动/省电页，失败回落应用详情 |
| 通知权限 | `NotificationManager.areNotificationsEnabled()`（T+） | 运行时请求 `POST_NOTIFICATIONS` |
| 蓝牙权限 | `BLUETOOTH_CONNECT` 自检（S+） | 运行时请求 |

**服务未启用与启用后被杀的区分**（`StabilitySnapshot.serviceEnabled`，读 `Settings.Secure.ENABLED_ACCESSIBILITY_SERVICES`，
用 `ComponentName.unflattenFromString` 比较 `pkg/.Cls` 短形式）：两者处理动作不同 —— 前者去无障碍里打开，后者才查省电策略。
判定层（`issues()`）不做区分，只要没在跑就报一项；区分只发生在文案层。

### 小米（HyperOS / Powerkeeper）的官方口径

小米官方文档（`dev.mi.com/xiaomihyperos` 文档 pId=1628）明确：**被 Powerkeeper 限制时 `isBackgroundRestricted()` 返回 `true`**，
用户把省电策略改成「无限制」后该值变为 `false`。这是可直接检测的官方信号，不需要猜后台是否被杀。

## Android 17（API 37）的行为变更与本项目的关系

| 变更 | 对本项目的影响 | 处理 |
|---|---|---|
| 新增 `ACCESS_LOCAL_NETWORK` 运行时权限（NEARBY_DEVICES 组） | 只影响局域网访问；本项目走蓝牙/RFCOMM，不做局域网 | 暂不声明。**升 targetSdk 37 前必须复查** |
| 后台音频强化：任何应用在后台做音频（播放/焦点/音量 API）必须有可见 Activity 或非 `SHORT_SERVICE` 类型的前台服务；targetSdk 37 时还要求带 WIU 的前台服务 | `connectedDevice` 类型 FGS 满足「非 SHORT_SERVICE」，但**服务没在跑时音量键会静默失效** | 本屏把「服务没在跑」摆在第一项；不解音量键问题，只让它可诊断 |
| MessageQueue 无锁化 | 本项目不反射私有字段 | 无关 |
| 静态 final 字段不可改 | 未使用 | 无关 |
| 应用内存限制 | 长日志页已按 1MB 截断 | 已满足 |

已核对：`foregroundServiceType="connectedDevice"` 与 `FOREGROUND_SERVICE_CONNECTED_DEVICE` 均已正确声明（targetSdk 34+ 的硬性要求已满足）。

## 权限声明

`AndroidManifest.xml` 新增：

```xml
<uses-permission android:name="android.permission.REQUEST_IGNORE_BATTERY_OPTIMIZATIONS" />
```

只用于 `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` 直接弹系统确认框。侧载自用、不上架，不涉及商店对该权限的限制政策。
其余权限（`POST_NOTIFICATIONS`、`BLUETOOTH_CONNECT`、`FOREGROUND_SERVICE_CONNECTED_DEVICE`、`WAKE_LOCK`）此前已存在。

## 厂商自启动页

`StabilityLogic.autostartComponent(vendor)` 按 `Build.MANUFACTURER` + `Build.BRAND` 识别（大小写不敏感，子品牌跟母品牌：
Redmi/POCO→XIAOMI、Honor→HUAWEI、realme→OPPO、iQOO→VIVO）：

| 厂商 | 组件 |
|---|---|
| 小米 | `com.miui.securitycenter/com.miui.permcenter.autostart.AutoStartManagementActivity` |
| 华为 | 华为自启动管理页 |
| OPPO / OnePlus | OPPO 自启动页 |
| vivo | vivo 后台启动管理 |
| 魅族 | 魅族权限管理 |
| 三星 / 通用 | `null`（明确约定：调用方必须回落应用详情，不假定入口存在） |

三层回落：厂商组件 → `ACTION_IGNORE_BATTERY_OPTIMIZATION_SETTINGS` → `ACTION_APPLICATION_DETAILS_SETTINGS`，
`ActivityNotFoundException` 与 `SecurityException` 都兜住并 Toast 说明。
真机（HyperOS 3）实测：小米组件存在且能打开；识别结果为 `XIAOMI`，指引落到小米那段 4 条步骤。

## 厂商指引文案

`res/values/strings.xml` 与 `res/values-zh-rCN/strings.xml` 各一套 `string-array stability_vendor_steps`（12 条），
按厂商切区间：小米 0–3、华为 3–5、OPPO/OnePlus 5–7、vivo 7–9、其余（三星/魅族/通用）9–end。
不照抄网上过时教程，避免用户按旧路径找不到菜单。

## 没做也不会假装做了的

- **未实测「被杀后重进」路径**：需要真机把服务置于后台受限再复现，本轮只验证了正常状态与未启用状态的读数。
- **未在华为/OPPO/vivo 真机验证厂商组件名**：只有字符串常量与三层回落保护，非这些机型上必然走回落。
- **`ACCESS_LOCAL_NETWORK` 未声明**：本项目不用局域网；若将来做，升 targetSdk 37 时必须补。
- **targetSdk 仍是 35**：升 36/37 的前置是边到边（`enableEdgeToEdge` / `WindowInsets`，全仓零使用）与预测性返回，见 `16-发布工程差距.md`。
- **未做「保活白名单一句话引导」之外的通知渠道运营**：通知权限只做检测与请求，不改变前台服务通知形态。
