# 21 - 静态检查与协程升级

这一批做两件事：把 detekt 接成「只拦新增债务」的门禁，把 coroutines 从 1.7.3 升到 1.9.0。

## 一、detekt：只拦新增债务

### 为什么不引 Gradle 插件

detekt 1.23.7 的 Gradle 插件面向 Gradle 8 API，本项目是 Gradle 9.4.1，插件有兼容风险。
所以直接用 `detekt-cli` 跑 `JavaExec`，两个任务写在根 `build.gradle`：

| 任务 | 作用 |
|:--|:--|
| `gradlew detektCheck` | 扫主模块与服务，只报 baseline 之外的新问题；有新问题则**构建失败** |
| `gradlew detektBaseline` | 重新生成 baseline（改了大段老代码之后跑） |

扫描范围：`brailleback/src`、`service/src`、`client/src`、`libraries/utils/src`、
`libraries/compatutils/src`；排除 `**/build/**`、`**/jni/**`、`**/*Test.kt`。
`addon/` 是上游移植代码，不动它，不扫。

### baseline 里冻结了什么

`config/detekt/baseline.xml`，**284 条**，约 39 KB。都是存量问题，冻结后不再报。
主要类别（不是风格洁癖，是真实的维护性问题）：

- `BrailleBackService`：类过大、39 个函数
- `BrailleBackService.onMappedInputEvent`：圈复杂度 15
- `BrailleFileDecoder.detectKind`：圈复杂度 17
- `BrailleFileDecoder.collapseBlocks`：嵌套过深
- `BrailleReaderActivity`：45 个函数、`setBrailleStream` 7 个参数
- `BrailleView.onDraw`：84 行、圈复杂度 19

### 阈值（`config/detekt/detekt.yml`）

不追 detekt 默认值（类内 11 个函数、方法 60 行、类 600 行）——现有代码本来就在默认值之上，
卡那么紧会让任何一次小改动都触发重排。当前设定：

| 规则 | 值 | detekt 默认 |
|:--|:--|:--|
| `TooManyFunctions.thresholdInClasses` | 30 | 11 |
| `LongMethod.threshold` | 100 | 60 |
| `LargeClass.threshold` | 900 | 600 |
| `CyclomaticComplexMethod.threshold` | 22 | 15 |
| `LongParameterList.functionThreshold` | 9 | 6 |
| `NestedBlockDepth.threshold` | 6 | 4 |
| `MaxLineLength.maxLineLength` | 160 | 120 |

关掉两条对硬件代码没意义的：`MagicNumber`（盲文点阵、HID 常量、超时到处都是）、
`ForbiddenComment`。`MatchingDeclarationName` 也关了，移植代码沿用上游命名。

### 门禁真的有效吗（验证过，不是只看它通过）

`detektCheck` 在 baseline 存在时通过，但这可能只是「baseline 覆盖了一切」假象。
所以做了一次探针：临时新建一个 `when` 有 24 个分支的方法（圈复杂度 26 > 阈值 22），

```
DetektGateProbe.kt:6:9: The function tooComplex appears to be too complex based on
Cyclomatic Complexity (complexity: 26). Defined complexity threshold for methods is set to '22'
> Task :detektCheck FAILED
```

**确实拦住了**，随后删除探针、重新跑 `detektCheck` 恢复通过。

### CI

`.github/workflows/ci.yml` 新增 `detekt` job（独立于单测与 lint，20 分钟超时），
跑 `./gradlew detektCheck -x verifyNativeLibs`。三条门禁并存：单测、detekt、lint。

## 二、coroutines 1.7.3 升到 1.9.0

### 改了三处

| 文件 | 改动 |
|:--|:--|
| `libraries/utils/build.gradle` | `kotlinx-coroutines-android` 1.7.3 → 1.9.0 |
| `service/build.gradle` | 同上 |
| `brailleback/build.gradle` | `kotlinx-coroutines-test` 1.7.3 → 1.9.0（虚拟时间必须同版，否则 `runTest` 语义对不上） |

原来的注释写的是「与 Compose 1.7.6 传递进来的 coroutines 对齐，避免解析出两套」。
升级后 Compose 传递的 1.7.3 会被统一抬到 1.9.0（`dependencyInsight` 实测：整棵依赖树
只有 1.9.0 一个版本，没有两套），注释同步改写。

### 为什么值得升

1.7.3 到 1.9.0 之间修掉的问题，正好落在本项目最敏感的地方：

- `Dispatchers.Main` 在 Looper 边界的行为
- `Job.cancel` 的竞态
- `StateFlow` 并发 emit 的丢失

`DisplayManager` 的定时器、光标闪烁、250 ms 合并窗口全部依赖协程调度，
这几类 bug 在盲文点显器上的症状就是「偶尔少刷一帧」「闪烁卡一下」，极难归因。

### 验证到什么程度

| 项 | 结果 |
|:--|:--|
| 主模块单测 | 50 套件 / 520 用例，全绿 |
| service 单测 | 23 套件 / 164 用例，全绿（含虚拟时间验证定时器的用例） |
| 真机启动 | debug 包装机后主进程起来、`Crashed services:{}`、无 `UnsatisfiedLinkError` |
| release 体积 | 17.75 MB，与升级前一致（R8 后无增长） |
| debug 体积 | 39.49 MB（比上一批记录的 33.34 MB 大 6.15 MB） |

**debug 那 6 MB 不是这次升级带来的**：做了对照构建，把 coroutines 临时改回 1.7.3 重新打包，
体积同样是 39.49 MB。差异来自其他构建状态（release 未变可佐证真实代码没变多），未继续深挖。

### 仍未验证的（真机，需要点显器在手）

- 滚动停下只刷一次
- 空闲三分钟清屏
- 光标闪烁节奏
- `setContent` 250 ms 合并窗口无空白帧

这四项本来就在未验收清单里，这次升级没有替它们作证。协程调度一变，它们是最可能受影响的地方，
**下次插点显器做实机验收时，这四项要一起看**。

## 三、下次怎么做

```powershell
# 日常门禁（三条，和 CI 一致）
.\gradlew.bat :brailleback:testDebugUnitTest :service:testDebugUnitTest --offline
.\gradlew.bat detektCheck --offline
.\gradlew.bat :brailleback:lintDebug --offline

# 改了大段老代码、detekt 开始报存量问题时，重新冻结
.\gradlew.bat detektBaseline --offline
```
