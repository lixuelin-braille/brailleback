## 一、现象与机关：为什么「插 USB 也不走 USB」

### 现象

真机持久化偏好里 `connection_protocol = bluetooth`，日志全程只有
`protocol=bluetooth route=BLUETOOTH`，零 USB 尝试；设备是 metec 40 方（42 格）
USB，VID:PID `0452:0100`，`usb_devices.c` 已有 `mt` 驱动条目。插不插线都进
蓝牙分支，点显器没反应。

### 机制（真实机关）

旧读路径把偏好缺省（`null`）直接交给 `ConnectionProtocolPolicy.normalize`，而
`normalize(null)` 折成 `BLUETOOTH`。于是：

1. 新用户从没写过协议值 → 读到 `null` → 被归一成 `bluetooth`；
2. 路由按蓝牙起手，AUTO 分支根本进不去；
3. 即便后续补了「自动」选项，缺键用户仍被这条默认值按在蓝牙上，USB 探针再准
   也没有机会被判定。

同类写法在两处：服务侧 `getConnectionProtocol()` 与 Compose 设备页 / 主屏迁移。
迁移函数还会把 `null != normalized` 当真值回写，等于把「没选过」静默改写成
「选了蓝牙」。

### 改法

- 新增 `ConnectionProtocolPolicy.DEFAULT = AUTO` 与 `readOrDefault(raw)`：缺键
  保留为 AUTO / 未决，只有显式手动值（`bluetooth` / `usb`）才归一钉死；
  `normalize(null) = BLUETOOTH` 这条既有兼容口径不动，避免牵动老用例。
- 迁移路径遇 `null` 直接 `return`，不落库、不归一化；已有手动值不被静默改写。
- 影响面：只改连接路由的起手判定，不动既有播报文案口径（新增播报除外）。

## 二、AUTO 判定顺序（纯函数，JVM 可测）

`AutoConnectionRouter.route(AutoRouteInput)` 不 import 任何 `android.*`，输入为
持久化偏好、USB 探针（VID/PID + 驱动码）、蓝牙是否开启 / 是否有已配对已知点显、
HID 控制器是否可用；输出起手路由 + 播报口径 + 是否保持当前档重扫 + 降级原因。

判定顺序：

1. **已知盲文 USB 设备**（命中 brltty `getUsbDriverTable()`，口径沿用既有
   `usb_devices` 表）→ USB 串口（`USB_SERIAL`）；
2. 否则**蓝牙开启且有已配对已知点显** → 蓝牙（`BLUETOOTH`）；
3. 两者皆无 → **保持当前档 + 进入周期性重扫**，不静默失败：带等待播报 / 日志，
   等插拔广播或既有退避周期再判。

手动档优先级最高：协议点名蓝牙 / USB，或链路点名非 auto 时，路由直接委托既有
`HidTransportRouting.resolve`，AUTO 判定不介入，选了手动就绝不自动切。

## 三、事件驱动重扫与幂等

- 注册 `USB_DEVICE_ATTACHED` / `USB_DEVICE_DETACHED`（33+ 沿用仓库既有写法带
  `RECEIVER_EXPORTED` / `RECEIVER_NOT_EXPORTED`）；插入即时重算路由并切换，
  拔出断开后由既有释放 / 退避周期重扫。
- 蓝牙侧复用既有 `BluetoothDiscoveryPolicy` / `DeviceFinder`，不新造一套；AUTO
  下的后台发现仍是既有有限时长窗口（`DISCOVERY_SESSION_DURATION` / 用户窗口
  `USER_DISCOVERY_WINDOW_DURATION`），不常驻扫描。
- 切换幂等由纯函数 `AutoSwitchGuard` 判定：
  - 同一路由 + 同一设备 → 重复 attach 广播幂等忽略；
  - 同一设备 **60 秒冷却窗口**内不重复换链路；
  - USB 优先由路由器保证，守卫只挡来回切。
- 拔出时清掉幂等状态：重新插上属于一次新的连接周期。

## 四、sdk=37 下 HID 不可用显式降级

`BrailleDisplayController` 不可用时：

- AUTO 不判 HID 失败、不等控制器复活：蓝牙路径直接落经典串口（RFCOMM），
  USB 路径降级到 `usb_serial`；
- 降级原因写进日志（`AUTO: HID controller unavailable...` /
  `AUTO: USB HID unavailable; degrading to usb_serial`），供以后真机复验；
- 手动档维持既有口径：等待控制器或报既有不可用文案，不被 AUTO 改动。

## 五、`.ktb` 表文件检出 EOL 问题（环境，非代码）

`KeyTableArchiveContractTest` 逐字节比对 `service/tables/keytables/sk/ntk.ktb`
与 `res/raw/keytables.zip` 内条目。新 worktree 检出时 `core.autocrlf=true` 把
blob 为 LF 的 `.ktb` 转成 CRLF 落盘（51 处 CR/LF 分歧，1686 vs 1635 字节），
包内条目仍是 LF，比对失败。主仓库老 worktree 同文件 `w/lf`、同测 4/0/0 全绿，
blob / zip / main 磁盘三者一致为 LF，定性为**检出环境问题，不是本轮代码回归**。

处理：`.gitattributes` 按扩展名收 `*.ktb -text`，按二进制原样落盘，覆盖
`service/tables/keytables/**` 与 `键位表试验/ntk.ktb` 两处；不加全局
`text=auto`、不整目录一刀切、不扩到 `.kti`、不改任何表文件字节。复核两条
`ntk.ktb` 均为 `i/lf w/lf attr/-text`。

  / 0 / 0 / 0；`:brailleback:assembleDebug` 成功。
