# 18 - 连接方式：新增「自动」

> 生成日期：2026-11-15
> 触发问题：`连接方式` 只有「蓝牙连接 / USB 连接」两项，选错了就是一串静默失败。
> 真机上当时存的是 `usb`，插着的却是蓝牙点显器，状态行只有一句
> 「USB 有线连接失败：No attached USB device matches the brltty driver table」——用户不会想到是选项错了。

## 自动的含义（一句话）

**插着点显器走 USB，没插走蓝牙。** 不是「先试 HID 再试串口」那种旧意义的 auto：
旧 `auto` 是无线内部的取舍（HID → RFCOMM），现在它被提升为第三种独立选择。

判定发生在**每次连接尝试**，不会在设置时固定：

```
connectBraille()
  ├─ usb             → connectUsbUnified()          // 用户明确选 USB
  ├─ auto + 探到线   → connectUsbUnified()          // 插着就优先有线
  └─ 其余            → connectBluetooth()           // 无界 BLE → HID → RFCOMM
```

「探到线」= 当前 USB 设备列表里存在一个匹配 brltty VID/PID 表的设备
（`BrlttyWrapper.getUsbDriverTable()` + `UsbBrailleDevice.candidateDrivers`）。
探针刻意复用有线路径同一张表：`true` 就意味着 `connectUsb()` 能找到驱动，
不会出现「探到有设备、连上去又报 no match」的自相矛盾。
JNI 或 `.so` 异常一律降级为 `false`（走蓝牙），不让探针把服务拖崩。

## 为适配 auto 改动的四处判断

| 原判断 | 改动 | 不改会怎样 |
|---|---|---|
| `connectBraille()` 二分支 | 加 auto 分支 | 自动永远走蓝牙，选它等于没选 |
| `isBluetoothProtocol()` = `bluetooth == value` | 改成 `!isUsbProtocol()` | auto 下 `isHidRequested()` 为 false，HID 永不尝试 |
| USB 插入广播的 `isWiredProtocol()` | 加 `isWiredOrAutoProtocol()` | 自动模式下插线不会触发切换 |
| `shouldAutoReconnect()` 的 `isWiredProtocol()` 直通 | auto + 探到线也直通 | 蓝牙关着且插着线时不再自动重连 |

`isWiredProtocol()` 本身保持「只认 USB」不变：它管的是「有线协议要不要无视蓝牙开关」，
auto 在没插线时必须受蓝牙开关约束，两者不能混。

## 归一化

`ConnectionProtocolPolicy.normalize()` 必须让 `auto` 原样通过 —— 折成 `bluetooth` 就等于这一项不存在。
顺带容忍大小写与空白（历史写入值可能是 `USB`、带空格），旧六种无线值仍折到 `bluetooth`。
`DeviceConnectionLogic.normalizeProtocol()` 直接复用服务端策略，两代 UI 不会读出不同值。

## 界面

选项顺序固定为 `bluetooth / usb / auto`（追加在末位，不改变原有顺序与默认值 `bluetooth`）。
`pref_connection_protocol_auto_label` 这条文案原本写的是「自动（先 HID，再蓝牙串口）」，
含义已变，中英同步改为：

- zh：自动（插着点显器走 USB，没插走蓝牙）
- en：Auto (USB when a display is plugged in, otherwise Bluetooth)

## 验证

```bash
gradle :service:testDebugUnitTest :brailleback:testDebugUnitTest
gradle :brailleback:lintDebug :brailleback:assembleDebug
```

- 主模块 50 套件 / 520 用例绿；service 23 套件 / 164 用例绿；lint error=0；debug APK 33.34 MB。
- 新增用例：`ConnectionProtocolPolicyTest`（auto 不被折成蓝牙、大小写空白容忍）、
  `DeviceConnectionLogicTest.labelForAutoReadsTheThirdEntry`、
  `UsbHidWiredContractTest.autoPicksWiredOnlyWhenADisplayIsActuallyPluggedIn`（并改名为
  `settingsExposeBluetoothUsbAndAuto` 的三项列表断言）。
- 真机（Redmi 24117RK2CC / Android 17）实测：弹窗三项顺序与选中态正确；
  选「自动」后存储值为 `auto`，状态行从「USB 有线连接失败」变为「正在查找：Orbit wujie 30」，
  即确实落到蓝牙路径去找已配对设备。

## 没做也不会假装做了的

- **未实测「自动 + 插着 USB 点显器」的分支**：真机当前没有可插的 USB 点显器，
  该分支只有单测与源码契约覆盖，没有真机走通一次 `connectUsbUnified()` 的记录。
- **未做「拔线后自动切回蓝牙」**：现在拔线走 `ACTION_USB_DEVICE_DETACHED` 的断开路径，
  之后由既有的自动重连按 auto 重新判定；没有专门的「立刻切蓝牙」逻辑，也没为此加测试。
- **`isUsbBrailleDeviceAttached()` 每次重连会读一次 JNI 表**：表很小（VID/PID 条目），
  按现有重连节奏（秒级）无压力；没有做缓存。
- **未在 HyperOS 上验证「省电限制会不会掐掉自动重连」**：那条线属于 `17-保活与权限适配.md`。
