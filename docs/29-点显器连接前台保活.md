# 29 · 点显器连接前台保活

> 2026-11-15。解决「蓝牙点显器连上后按返回、应用回后台就断连」。
> 相关：`17-保活与权限适配.md`（电池优化/厂商限制/权限自检）、`28-targetSdk37.md`（前台服务类型校验）。

## 1. 现象与日志证据

用户报告：蓝牙连上点显器后按返回，软件回后台，连接停止。

真机日志（`files/logs/brailleback.log`）：

```
17:11:27.988 I/brltty: Successfully initialized braille driver bm on device bluetooth:68:09:47:68:54:FE
17:11:28.994 I/BrailleService: Disconnecting braille display (pending=false)
17:11:28.996 I/BrailleService: Disconnecting braille display (pending=false)
```

同一动作在**无障碍服务开启**时复现不出来（17:11:59 连上，返回后 `conn=true` 一路继续）。

## 2. 根因

`DisplayService` 是纯绑定服务，连接寿命由客户端数决定：

- `onUnbind()` 里 `mClients.beginBroadcast()` 数在线客户端，`<= 0` 就 `cancelPendingReconnect()` + `disconnectBraille()`；
- 服务随后被系统销毁，`onDestroy()` 又无条件 `disconnectBraille()` —— 日志里那两行 3 ms 间隔的 `Disconnecting` 就是这两次调用。

客户端分布：

- 无障碍服务开启时，`BrailleBackService` 的 `DisplayManager` 常驻持有 `DisplayClient`，界面退出只是少一路客户端，不会归零；
- 无障碍服务没开时，阅读器/设置页本身就是**唯一客户端**。进入设置页时 `onBind` 触发 `autoConnectBraille()` 连上，按返回 → Activity 销毁 → `DisplayClient.shutdown()` 解绑 → 客户端归零 → 断开。

所以不是崩溃，也不是蓝牙栈问题，是「连接跟着界面走」的生命周期设计。

## 3. 方案

连接成功后把 `DisplayService` 提升为前台服务（`connectedDevice`），让服务变成 **started**；同时给服务一个显式的保活标志，`onUnbind` 在保活期间不再主动断开。

| 改动 | 位置 |
|:---|:---|
| 清单声明前台类型 | `brailleback/AndroidManifest.xml` 的 `DisplayService` 加 `android:foregroundServiceType="connectedDevice"` |
| 保活实现 | 新文件 `service/src/.../display/DisplayForegroundKeepAlive.kt` |
| 连接成功提升 | `DisplayService.onDisplayConnected()` → `promoteDisplayForeground()` |
| 补 `startForeground` | `DisplayService.onStartCommand()` 收到 `ACTION_DISPLAY_KEEP_ALIVE` 时调用 |
| 解绑保护 | `onUnbind()`：`clientCount <= 0 && !mDisplayKeepAliveActive` 才断开 |
| 断开撤销 | `disconnectBraille()` 末尾 `dropDisplayForeground()` |
| 文案 | `service/res/values/strings.xml`、`values-zh-rCN/strings.xml` 三条 `display_keepalive_*` |

关键取舍：

- **不新增常驻客户端**。多绑一个 `DisplayClient` 也能让客户端数不归零，但那是用「假客户端」骗过计数；改成 started + foreground 后，服务本身就活得比界面久，语义更正。
- **无障碍服务开启时不提升**，避免和 `BrailleBackService` 自己的常驻通知重复（实测只有 id=1 一条）。本包只有一个无障碍服务，所以按包名判断即可，`service` 模块不需要反向依赖应用模块的类。
- 后台（例如自动重连）不允许启动前台服务时，`startForegroundService` 抛 `IllegalStateException`：只记日志，不打断连接。
- Android 14+ 会校验 `connectedDevice` 的前置权限（如 `BLUETOOTH_CONNECT`）。`startForeground` 抛 `SecurityException` 时撤销前台并 `stopSelf()`，避免前台服务超时被判成 ANR。

权限清单本来就已经齐（`FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_CONNECTED_DEVICE`、`POST_NOTIFICATIONS`、`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`、`BLUETOOTH_CONNECT`），这次只补了服务类型声明和运行时兜底。

## 4. 真机验证（无障碍服务关闭）

```
dumpsys activity services com.googlecode.eyesfree.brailleback
  isForeground=true foregroundId=2 types=0x00000010
  startRequested=true
  foregroundNoti=Notification(channel=braille_display_keepalive ... flags=ONGOING_EVENT|NO_CLEAR|FOREGROUND_SERVICE)
```

- 进入设置页 → `17:25:42` 连上 → 按返回 → 10 秒后日志无 `Disconnecting`，`DriverThread` 统计仍在走；
- 服务仍 `isForeground=true`、`startRequested=true`；
- 通知标题「点显器连接保持中」，正文「退出界面后点显器仍保持连接；在系统里强制停止应用会断开」；
- 无障碍服务开启时只有 id=1 的原通知，没有第二条；
- `logcat -b crash` 无 brailleback 记录。

## 5. 边界与后续

- 强制停止应用、卸载、进程被系统回收都会断连；这是保活的上限，不是 bug。
- 目前没有界面内「断开」按钮：无障碍服务关闭时，停止方式只有关点显器或强制停止应用。要补的话，给通知加一个 `PendingIntent` 动作即可。
- 通知权限被拒时前台服务照常运行，只是通知不可见；保活自检页（`17-保活与权限适配.md`）已有该项状态与申请入口。
- MIUI 的内存/省电策略仍可能杀进程：需要在自检页把电池优化设为「无限制」并允许自启动。
- 结构护栏：`DisplayForegroundKeepAliveContractTest`（4 例）锁清单类型、提升/撤销调用、`onUnbind` 的保活判断，以及保活文件不膨胀。
