## 一、结论（前置，可直接朗读）

改前存在两个手感问题，都是用户在真机实测时发现的现象：

1. 翻页每页被压约 350ms。用户走 USB 连接时，运动模式被默认推导为开启，每次刷新都被运动去抖压住 `MOTION_MODE_DEBOUNCE_MS`（350ms，`brailleback/src/main/java/com/linxi/brailleback/DisplayManager.kt:799`，唯一生效点在同文件 `:745` 的 `motionDebouncer.schedule(...)`），停一下才补刷上屏。
2. 启动时几百毫秒一轮「不断重连」。启动期输入设备反复注册、系统广播重复到达，旧的自动重连只挡「已连上 / 在途」，没有最小间隔、没有去重，每条广播都立刻重拨一次；再叠 `HID_RETRY_DELAY = 300L`（`service/src/main/java/com/googlecode/eyesfree/braille/service/display/DisplayService.kt:102`），节奏就是几百毫秒一轮。

改后：

1. 运动模式不分连接方式一律默认关闭，单次刷新立即上屏，不再经过那 350ms 运动去抖。
2. 自动重连新增最小间隔 `AUTO_RETRY_MIN_INTERVAL_MS = 800L`（`service/src/main/java/com/googlecode/eyesfree/braille/service/display/AutoRetryGate.kt:123`）；同设备去重走独立窗口 `AUTO_RETRY_DEDUPE_WINDOW_MS = 2000L`（同文件 `:132`），不同来源互不干扰；另设连接后 settle 稳定期 `CONNECTION_SETTLE_MS = 1000L`（同文件 `:141`）。活跃态在进守卫之前先取到并喂进去，settle 起点才真正被记录。

问题来源与修复归属：上述真机现象由用户口头实测报告（约 600ms 一轮重连、翻页约 350ms 延迟）；本次修复由团队实现，未取得用户原始 diff。本文不表述为「用户提交的补丁」或「用户已修复」。

## 二、行为变更告知（给用户的一句话）

如果你之前用 USB 连接、并且从来没有在设置里手动拨过「运动模式」开关，升级后这项会变成关闭；点显器每次更新立即刷新。如果你需要「快速滑动时合并刷新、停下来再刷」，可以在「声音与行为 / Sound and behavior」里手动把运动模式打开。你手动拨过的选择永远优先于默认值，不会被这次改动覆盖。

## 三、改了什么

### 缺陷甲：翻页每页被压 350ms（运动模式默认开）

根因：

- 真凶不是常量，而是默认值推导。`BrailleBackService.applyMotionModeDefault`（`brailleback/src/main/java/com/linxi/brailleback/BrailleBackService.kt:656`）旧实现用 `ConnectionProtocolPolicy` 归一化协议，USB 为真就把 `pref_motion_mode_key` 写成 `true` 并下发；蓝牙才写 `false`。
- 用户当前走 USB，于是运动模式默认开着。每次刷新被 `RefreshBlock.MOTION` 挡住，`DisplayManager` 走 `motionDebouncer.schedule(MOTION_MODE_DEBOUNCE_MS)`（`DisplayManager.kt:745`）压 350ms 再补刷。

改法：

- 删掉「USB 默认开启」这条推导，改成不分协议一律默认 `false`。
- 用户显式拨过的原逻辑原样保留：`pref_motion_mode_explicit_key` 为 `true` 时，完全以用户存下的值为准，不再看连接方式。这条优先级没有动。
- 未显式拨过时，把 `pref_motion_mode_key` 归一化为 `false` 写回并下发；旧版本按 USB 推导写入过的 `true` 会被这次写回纠正。
- 生效值解析抽成纯函数 `SoundBehaviorLogic.resolveMotionMode(explicit, stored)`（`brailleback/src/main/java/com/linxi/brailleback/compose/SoundBehaviorLogic.kt`），便于 JVM 单测；服务方法仍保持原来「写回并回传」的写法习惯。
- 文案同步改：英文 `brailleback/src/main/res/values/strings.xml:251-252`、中文 `brailleback/src/main/res/values-zh-rCN/strings.xml:204-205`。新文案说清：运动模式默认关闭、需要时手动开启；开启后快速滑动合并刷新、停下再刷。

为什么不去改 350ms 这个值：

- `MOTION_MODE_DEBOUNCE_MS = 350`（`DisplayManager.kt:799`）一个字未改。它只在用户显式开启运动模式时生效，此时「压住再补刷」是设计意图。没有真机手感证据，不降到 100，更不归零。本次是把默认入口关掉，而不是把去抖本身调快。

### 缺陷乙：启动约 600ms 一轮「不断重连」

根因：

- `DisplayServiceConnectionFlow.retryHidWhenInputDeviceAppears()`（`service/.../display/DisplayServiceConnectionFlow.kt:262`）在输入设备出现时触发；`prepareAutomaticRetry()`（同文件 `:274`）旧实现只挡 `isConnectionActive()`，没有最小间隔、没有去重。
- 启动期输入设备反复注册 / 广播，每来一次就立刻重连一次；叠 `HID_RETRY_DELAY = 300L`（`DisplayService.kt:102`），节奏几百毫秒一轮。前科有据：`DisplayServiceHandlerActions.kt` 注释记着「47k retries in 17s, ~106% CPU」。

改法：

- 新增纯逻辑判据 `AutoRetryGate`（`service/.../display/AutoRetryGate.kt`），可注入时钟，JVM 可测，不碰 Android 框架类。
- 活跃态先取后喂：`prepareAutomaticRetry`（`DisplayServiceConnectionFlow.kt:274`）在进守卫之前先 `val active = isConnectionActive()`，再把 `active`、`inFlight`、`sourceKey` 一起传给 `shouldAllow`。活跃 / 在途的短路由守卫的 active 分支承担，语义与原先提前返回等价，但活跃观察不会被挡在守卫之外。
  - 第一轮曾把 `if (isConnectionActive()) return` 留在守卫之前：全仓唯一调用点就是这个函数，传给守卫的 `active` 恒为 false，`markActive` 永远收不到 `active = true`，settle 分支退化成死代码；单测是直接构造 `shouldAllow(active = true, ...)` 才变绿，测的是守卫自己、不是生产接线。本轮已按上述方式纠正，并补了一条源码契约断言守住接线。
- 最小间隔：`AUTO_RETRY_MIN_INTERVAL_MS = 800L`（`AutoRetryGate.kt:123`）。取不到稳定键（`sourceKey = null`）的触发退回这个全局最小间隔，防止无键触发成串重拨。为什么是 800：启动期设备注册 / 广播在数百毫秒内成串到达，300ms 的 `HID_RETRY_DELAY` 不足以隔开；800ms 足够吞掉同一轮枚举的重复广播，又不拖慢一次真实新设备出现后的首次重连（首次触发不受间隔约束）。
- 同设备去重独立窗口：`AUTO_RETRY_DEDUPE_WINDOW_MS = 2000L`（`AutoRetryGate.kt:132`）。HID 输入设备按广播 extra `deviceId` 归一为 `hid:<id>`，蓝牙按地址归一为 `bt:<address>`；同一 `sourceKey` 在 2000ms 内重复出现直接忽略，即使已过 800ms 最小间隔。窗口大于最小间隔，去重是一条独立成立的判据。
- 不同来源互不干扰：`sourceKey` 不同的触发不被别的设备的冷却 / 去重挡住；一条新设备插上不能被上一台设备的记账压住。
- settle 稳定期：`CONNECTION_SETTLE_MS = 1000L`（`AutoRetryGate.kt:141`）。守卫收到一次活跃（连上 / 在途）后记下起点，状态短暂回落空闲的这段时间内，迟到广播不判失败、不重试。这是判据核心：区分「刚连上、正在落定」与「空闲无设备」，不是靠把 backoff 间隔调大来压节奏。
- 在途尝试（`mConnectPending` / `mWaitingForHidController`）不被新触发打断。守卫被挡下时不调用 `cancelHidControllerTimeout()`、不重置标志，不取消、不重建进行中的连接尝试。

为什么不去调大既有 backoff：

- `HID_RETRY_DELAY = 300L`（`DisplayService.kt:102`）、`DISCOVERY_RESTART_DELAY = 300L`（同文件 `:118`）、`AUTO_RECONNECT_INITIAL_DELAY = 3000L`（同文件 `:109`）三个现有值原样未动。本次只挡启动期同来源的重复触发，不靠调大间隔掩盖问题。

## 四、用例账

基线（改动前，main `36f85ce`）与改动后均在同一台机器、同一套 Gradle 命令下跑双模块单测；判据是相对自身基线用例数不减、不新增失败。

- brailleback 模块：1078 例 → 1082 例（+4），失败 0、错误 0。
- service 模块：240 例 → 249 例（+9），失败 0、错误 0。

本轮要求补的四条用例，对应关系如下：

1. 1 秒内连续 5 次「HID input device appeared」只产生 1 次连接尝试。
   - `AutoRetryGateTest.five repeated HID appearances within one second produce a single attempt`（service）。注入可控时钟，5 次触发落在 0/120/240/360/480ms，断言只放行 1 次。
2. 运动模式默认关闭后，单次刷新不再经 `motionDebouncer`（不出现 350ms 延迟）。
   - `RefreshPolicyTest.默认关闭时单次刷新立即下发，不经运动去抖`（brailleback）。`motion = false` 时决策为 `Send`，不进 `Blocked(MOTION)` 分支。
3. 同一设备重复广播在窗口内被忽略。
   - `AutoRetryGateTest.same device repeated broadcast is ignored within the dedupe window`（service）。同设备 500ms、801ms（已过 800ms 最小间隔、仍在 2000ms 去重窗口内）均被挡；超过 2000ms 后同设备可再次放行（不是永久拉黑）。
4. 用户显式开启运动模式时行为与改前一致。
   - `RefreshPolicyTest.显式开启运动模式时仍走运动去抖，行为与改前一致`（brailleback）：`motion = true` 仍判 `Blocked(MOTION)`。
   - `SoundBehaviorLogicTest.显式选择永远优先于默认值`（brailleback）：`explicit = true` 时存什么用什么。

另外为判据本身与生产接线补的护栏用例（service）：

- `AutoRetryGateTest.different sources do not block each other`：另一台设备在 800ms 内出现，不被上一台设备的冷却 / 去重挡住。
- `AutoRetryGateTest.null source key falls back to global min interval`：取不到稳定键时退回 800ms 全局最小间隔。
- `AutoRetryGateTest.settle period after being active does not judge late broadcasts as failures`：守卫自身在活跃后 settle 期内迟到广播不判失败，超期后才放行。
- `AutoRetryGateTest.active or in-flight attempt is never interrupted by a new trigger`：已连上或在途尝试不被新触发打断。
- `AutoRetryGateTest.first trigger with no history is allowed`：无历史的首次触发不受间隔约束。
- `AutoRetryWiringContractTest.active state is read before the gate and fed into shouldAllow`：源码契约断言 `prepareAutomaticRetry` 先取 `val active = isConnectionActive()` 并把 `active` 喂进 `shouldAllow(active, inFlight, sourceKey)`，防 settle 再退化成死代码。
- `AutoRetryWiringContractTest.no early active return shadows the gate`：源码契约断言函数体内守卫之前不再有 `if (isConnectionActive())` 提前返回。

覆盖口径说明：settle 的守卫内部逻辑由 `AutoRetryGateTest` 直接构造 `shouldAllow(active = true, ...)` 覆盖；生产路径是否真的把活跃态喂进守卫，由 `AutoRetryWiringContractTest` 从源码层面另守一条。两条合起来才算 settle 在生产路径上落地，不单靠其中一条。

测试确定性说明：`AutoRetryGate` 注入 `clock: () -> Long`，用可变 now 驱动，不起蓝牙、不依赖 Android 框架类，没有真实长 sleep；`DisplayManager` 内部计时结构（`motionDebouncer` / `MOTION_MODE_DEBOUNCE_MS` 的机制本身）属于禁改区，未为好测去重写。
