# 133 · 发布签名密钥决定与保管

> 日期：2026-11-26
> 裁决背景：产品负责人已把密钥事项整体授权给团队；本记录为 ENGINE 线发布密钥专项的决定留档。
> 关联文档：[121-发布工程与密钥保管](./121-发布工程与密钥保管.md)（在 `chore/release-readiness` 工作树 `D:\bb-wt\release`，尚未合入 main）、[125-下一步功能优化方案](./125-下一步功能优化方案.md) §7。
> 安全红线：本文档不记录任何密码明文；密码只存在于仓库外的 `keystore.properties` 与密码文本两处文件里。

## 1. 团队决定与理由

**决定：复用现有一把 release keystore `D:\keys\brailleback-release.jks`，不新生成、不覆盖、不重做。**

理由：

1. 它已满足团队全部口径：放在仓库外、不进版本库、RSA 4096 位、有效期 10000 天、PKCS12 格式。
2. 121 分支的 `keystore.properties` 已经指向这把钥匙，接线是现成的；另生成一套等于把已接好的线拆掉重接，徒增指纹与备份口径混乱。
3. 密钥一旦签过对外包就不可回收；手上只有一把可追责的钥匙，比两把钥匙各管一部分要清楚。

同时明确：**不沿用 debug 证书**。`CN=Android Debug` 证书只用于开发自测，不能用于发布；主仓库当前产物仍是 debug 签名（见 §4 查证记录）。

## 2. 现有密钥参数（不含密码）

- keystore 文件：`D:\keys\brailleback-release.jks`
- storetype：PKCS12
- alias：`brailleback-release`
- 条目类型：`PrivateKeyEntry`（自签，Owner = Issuer）
- 证书 DN：`CN=BrailleBack, OU=Braille Service, O=BrailleBack, C=CN`
- 公钥算法 / 位数：RSA 4096 位
- 签名算法：SHA384withRSA
- 有效期：2026-11-26 16:39:46 CST 起，至 2054-04-13 16:39:46 CST 止（10000 天）

**口令一致性核查**：`keystore.properties` 中的 `storePassword`、`keyPassword` 与同目录密码文本三处口令，经 SHA-256 哈希比对**一致**；`storePassword` 与 `keyPassword` 相同。本文档不记录口令，也不记录口令哈希。

## 5. 备份指引（供产品负责人照做）

需要复制的只有两个文件：

- `D:\keys\brailleback-release.jks`（密钥库）
- `D:\keys\brailleback-release-密码.txt`（密码文本）

步骤：

1. 准备两份不同介质的存放地点：例如一个加密 U 盘，加一个离线硬盘或网盘；两处不要放在同一个袋子，也不要插在同一台电脑上。
2. 先备份密钥库：把 `brailleback-release.jks` 复制到第一处介质。复制完成后，在该介质上能朗读出这个文件名，即视为文件已到位。
3. 再备份密码文本：把 `brailleback-release-密码.txt` 复制到第二处介质。注意：密码文本不要和 jks 放在同一个介质里。
4. 以后每次更换密码或换密钥，都按这两步重新备份；旧备份介质上的旧文件随之作废。

**为什么密码和 jks 要分开存**：jks 是锁，密码是钥匙。放在同一个 U 盘里，这个 U 盘一丢，锁和钥匙一起丢，等于整体失控；分开存，单个介质丢失后，还能凭另一处的密码配合剩余 jks（或反之）恢复。

**丢了会怎样**：Android 覆盖安装要求新旧包签名一致。jks 丢了或密码丢了，就再也给已安装的旧版本做覆盖升级；只能改包名发一个全新应用，旧用户的阅读进度、书签、点显器配对状态都带不过去。

日常红线：不要在截图、聊天记录、issue、提交信息、构建日志里粘贴密码；密码文本只存在于本机与备份介质上。

## 6. 接线预告（接口说明，接线由 ENGINE 完成）

- 构建侧回落策略：`brailleback/build.gradle` 读取仓库根 `keystore.properties`；文件存在则用 `signingConfigs.release` 签名，缺失则 release 回落 `signingConfigs.debug`，保证不配密钥也能打包。
- 121 合入 main 后，由 ENGINE 在合入接线时把本机 `keystore.properties` 放到仓库根并指向本把钥匙；字段形状：`storeFile`（正斜杠绝对路径 `D:/keys/brailleback-release.jks`）、`storePassword`、`keyAlias`（`brailleback-release`）、`keyPassword`。
- `.gitignore` 已覆盖 `keystore.properties`、`*.jks`、`*.keystore`，接线时无需再补忽略规则。
- 本专项不在主仓库放置 `keystore.properties` 实体，也不改构建脚本；只留本接口说明。

## 7. 验签方法

在装有 build-tools 37.0.0 的机器上（本机路径 `C:\tools\android-sdk\build-tools\37.0.0\apksigner.bat`）：

```
apksigner verify --print-certs <apk 路径>
```

release 包通过后期望出现：

- certificate DN：`CN=BrailleBack, OU=Braille Service, O=BrailleBack, C=CN`
- certificate SHA-256 digest：`e0bf6b261930030949a944c815015e477b80723d0bae72c08a2db0d331f1968a`
- certificate SHA-1 digest：`753a22f929b93bd6d796aa52db506ea09d21af48`
- 退出码 0。

从密钥库侧复核（会提示输入口令，口令见密码文本，不要回显到文档或聊天里）：

```
keytool -list -v -keystore D:\keys\brailleback-release.jks -alias brailleback-release
```

一致性口径：把 keytool 输出的 SHA256 去掉冒号、转小写，与 apksigner 的 SHA-256 digest 逐字节比对，两者必须相同。

## 8. 风险提示

- 这把密钥一旦用于正式对外发布，就不可更换：后续所有升级包必须用同一把钥匙签名；换钥匙等于换应用，老用户无法覆盖升级。
- 当前未证实已有对外发布包使用此密钥；但在任何一个对外版本发布之后，本把 jks 与密码即成为不可丢失、不可替换的资产，备份与分介质保管必须在首次对外发布前完成。
- 不要自行生成第二把 release 密钥替代本把；如需更换，属于产品负责人书面授权的专项决定，不在日常迭代范围内。
