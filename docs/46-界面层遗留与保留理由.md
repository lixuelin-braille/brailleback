# 46 · 界面层遗留：哪些是真痕迹，哪些是刻意保留

本文记录「去老项目痕迹」收尾阶段的判定结果。结论先给：**界面层剩下的 XML 不是历史包袱，是有技术理由的保留**。真正的历史痕迹已经在 A/B 两档和本轮资源清理里清掉了。

## 2. 六个 XML 布局的逐个判定

| 布局 | 行数 | 引用点 | 判定 |
| --- | --- | --- | --- |
| `overlay.xml` | 48 | `OverlayDisplay.kt:394`、`OverlayTutorialActivity.kt`（两处 include） | **保留** |
| `braille_ime.xml` | 37 | `BrailleIME.kt:278` | **保留** |
| `activity_licenses.xml` | 6 | `WebViewDialog.kt:44` | **保留** |
| `braille_reader.xml` | 99 | `BrailleReaderActivity.kt:153` | 可迁移，但收益低 |
| `search_tutorial_activity.xml` | 41 | `SearchTutorialActivity.kt:49` | 可迁移，但收益低 |
| `overlay_tutorial_activity.xml` | 68 | `OverlayTutorialActivity.kt:58` | 可迁移，但与 `overlay.xml` 强耦合 |

### 2.1 `overlay.xml` 必须保留

它包含自研 `BrailleView`（自定义 `onDraw`，带 `dotRadius/cellWidth/cellHeight/cellPadding/highlightDrawable` 五个自定义属性）。在 Compose 里只有两条路：

- `AndroidView` 包一层 —— 等于没改，还多一层；
- 重写成 Compose `Canvas` —— 但 `OverlayDisplay` 是高频重绘路径（`BlinkPolicy` 按 600/800 ms 闪烁、`highlightCell` 逐格高亮），盲文点阵每帧重算布局的成本直接落到光标跟读的延迟上，这是本项目最不能碰的性能红线（见 docs/01 稳定性方针）。

**自定义 View 画点阵不是「老写法」，是这类渲染的正确写法。** Compose 官方对高频自绘场景同样推荐保留 View/Canvas。

### 2.2 `braille_ime.xml` 必须保留

它在输入法窗口里 inflate，而 IME 的 `onCreateInputView` 有硬性的启动时延预算；输入法面板是最不该引入 Compose 组合开销的地方（Compose 首次组合 + 语义树初始化在低端机上可见地慢）。且该布局只有 3 个控件：图标、标题、副标题。

### 2.3 `activity_licenses.xml` 无需改

整个文件就是一个 `WebView`（id `content`）。Compose 化只能得到 `AndroidView { WebView }`，零收益。

### 2.4 两个教程页 + 图书阅读页：能改，但不建议现在改

- `SearchTutorialActivity` / `OverlayTutorialActivity` 是**引导页**，用户一生只看一两次，跑在 `DeviceDefault` 主题下的 `Activity`/`ComponentActivity` 上。改成 Compose 带来的唯一收益是「代码风格统一」，用户感知为零。
- 但成本不低，且有明确回归风险：项目里 `CoroutineScopeContractTest` 与 `DeveloperOptionsContractTest`（第 257 行起）对这两个类的源码**逐字断言**（`lifecycleScope.launch` + `delay(...)`、`startIfFirstTime`、`startActivity(Intent(this, OverlayTutorialActivity::class.java))`、禁止 `object : Runnable`、禁止 `postDelayed(`）。改 UI 必须同时保持这些字面契约，否则测试红。
- 更关键：**当前环境没有可用设备**（`adb devices` 为空），改完无法验证 TalkBack 朗读顺序、点显器连接状态切换、`startSearchMode` 触发时机。这些恰恰是引导页的全部价值。

`braille_reader.xml` 同理：8 个按钮 + 文本区，属于读者主界面，改动后必须真机跑一遍完整阅读流程才敢发布。

## 3. 最后一处 `PreferenceFragmentCompat`

现状：全项目只剩 `CustomKeyMapActivity.kt` 里的 `CustomKeyMapFragment` 仍在用 `androidx.preference`（`ListPreference` / `PreferenceCategory` / `PreferenceScreen`），其余设置页在 docs 40–43 已全部 Compose 化。

它没有立刻迁移的原因：

1. 它是**编辑器**，不是开关页。每个按键动作是一行 `ListPreference`，选中弹单选对话框，并要按点显器实际按键数动态生成行——Compose 化要重做「动态生成 + 对话框 + 空键位回退」三段逻辑。
2. `KeyMapResourceContractTest` 断言它**必须仍然存在**、且 `KeysGesturesComposeActivity` 用 `Intent(..., CustomKeyMapActivity::class.java)` 启动它。类名和入口不能动，只能换内部实现。
3. 这是用户改键位的唯一入口，改错等于盲文用户失去自定义能力——需要真机 + 点显器验证。

**建议**：作为独立一批改造（迁移 + 同步改写 `KeyMapResourceContractTest` 的断言 + 真机回归），不要和教程页混在一起做。

## 4. 主题三套并存的真相

| 主题 | 用在哪 |
| --- | --- |
| `BraillebackTheme`（`Theme.DeviceDefault`） | 主应用绝大部分 Activity，含 overlay、IME、教程页 |
| `BraillebackSettingsTheme`（`Theme.AppCompat.DayNight.DarkActionBar`） | 设置相关页面与 Compose Activity 宿主 |
| Compose `MaterialTheme`（material3 1.4.0） | 所有 Compose 页面，在 `SettingsScaffold` 内部套 `colorScheme` |

这不是「三套风格打架」：Compose 页面由 `SettingsScaffold` 自己下发 colorScheme，XML 主题只负责窗口背景、状态栏与旧控件外观。合并成单一 Material3 主题的唯一实际动作是把 `BraillebackTheme` 的 parent 换成 `Theme.Material3.*`，但这会改变 overlay（`#C0000000` 半透明浮层）与 IME（`#cc000000`）的窗口装饰行为——**为一个观感收益去动最不敢动的两个界面，不划算**。

## 5. `addon` 198 个 Java 文件为什么不转 Kotlin

`addon/` 是 TalkBack 屏幕盲文键盘的移植代码（198 个 Java / 30,126 行，自带 `ndk-build`），与本项目主线（`brailleback` + `service` 的中文盲文引擎）只有接口级耦合。项目方针是「不迁移到 TalkBack，专注稳定性」（docs/01）。批量转 Kotlin 会产生 3 万行无法逐行复核的 diff，且没有任何用户可见收益。**保持原样是正确决定，不是遗漏。**
