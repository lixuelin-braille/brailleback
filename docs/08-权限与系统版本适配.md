## 关于小米「输入密码/指纹」验证的重要更正

用户反馈：小米手机上开权限要点「更多 → 允许权限 → 输入密码」。

**根因不是 targetSdk**，而是 Android 13 引入的
**「受限设置（Restricted Settings）」**机制：
检测到应用**通过非官方渠道安装（侧载）**且申请**高危权限（无障碍服务、通知监听）**时，
系统底层锁死权限开关。解锁路径：设置 → 应用管理 → 该应用 →
**右上角三点 → 允许受限设置 → 验证指纹/密码**。

结论：
- **代码无法消除**该验证——它是系统级反滥用保护，对本应用（无障碍服务）必然触发
- 升 targetSdk 解决的是「权限批量弹窗」问题，与本验证无关
- **可行缓解**：
  1. 应用内引导文案（告知用户右上角三点 → 允许受限设置）
  2. 从应用商店分发安装（非侧载则不触发受限设置）
  3. 用户其他项目「不用输密码」多半因为：不是无障碍类应用，或经商店安装

## 二、当前基线

```
compileSdk  35（:brailleback / :service）   34（:client / :libraries:*）
minSdk      23（Android 6.0）
targetSdk   34（Android 14）   ← 问题所在
```

权限声明全清单（`brailleback/AndroidManifest.xml`）：

```xml
<uses-permission android:name="android.permission.WAKE_LOCK" />
<uses-permission android:name="android.permission.BLUETOOTH"
                 android:maxSdkVersion="30" />
<uses-permission android:name="android.permission.BLUETOOTH_ADMIN"
                 android:maxSdkVersion="30" />
<uses-permission android:name="android.permission.BLUETOOTH_CONNECT" />
<uses-permission android:name="com.googlecode.eyesfree.braille.display.PERMISSION_CONNECT" />
<uses-permission android:name="com.google.android.marvin.talkback.permission.LABELING" />
```

共 6 条，其中：

- 普通权限 1 条（`WAKE_LOCK`，自动授予）
- 危险权限 **1 条**（`BLUETOOTH_CONNECT`，需运行时请求）
- 自定义权限 2 条（`signature` 级，仅同签名应用可用）
- 旧蓝牙权限 2 条，已限定 `maxSdkVersion="30"`

**运行时实际只请求 1 个权限**，且在设置页按需触发  
（`BrailleBackPreferencesActivity.kt:448`）。

## 四、"要允许所有权限才可以"——成因分析

用户反馈的现象，最可能的原因是 **targetSdk 偏低**：

国产 ROM（MIUI / ColorOS / OriginOS 等）对 `targetSdk` 较低的应用会启用  
**兼容策略**：首次启动时把该应用声明的权限**一次性批量弹出**请求，  
而不是按运行时权限模型逐个、按需请求。用户感知就是"要允许所有权限才行"。

本项目虽然只声明了 1 个危险权限，但：

- 旧蓝牙权限（`BLUETOOTH`/`BLUETOOTH_ADMIN`）虽已限 `maxSdkVersion=30`，  
  部分 ROM 的权限列表仍会**展示**它们，让用户误以为要授予很多权限
- 提升 `targetSdk` 后，系统走标准运行时模型，这类批量弹窗会消失

> 也就是说：**不是权限声明有问题，是系统因为 targetSdk 低而走了兼容路径。**

## 五、改进方案

### 必须做（升 targetSdk 前）

1. **处理 edge-to-edge**（否则升级后设置界面可能被状态栏遮挡）
   - 新建 `res/values-v35/themes.xml`，对 Android 15+ 显式退出边到边强制：
     ```xml
     <style name="AppTheme" parent="...">
         <item name="android:windowOptOutEdgeToEdgeEnforcement">true</item>
     </style>
     ```
   - 这是**过渡方案**：该属性在 API 36 已废弃，长期仍需真正适配 insets
2. **统一 `compileSdk` 到 35**
   - 现 `:client` / `:libraries:utils` / `:libraries:compatutils` 仍是 34
   - 不影响运行，但统一后 lint 检查更准确

### 建议做

1. **`targetSdk` 34 → 35**（保守一步）
   - 消化 Android 15 行为变更
   - 改完必须真机验证界面与点显器连接
2. **规范化 `exported`**
   - `WebViewDialog` 无 intent-filter，默认 `false` 已合规，  
     但显式写出更清晰、也能避免将来加 intent-filter 时漏掉：
     ```xml
     <activity android:name="WebViewDialog" android:exported="false" />
     ```

### 可选（等稳定后再做）

1. **`targetSdk` 35 → 36**
   - Android 16 刚发布，行为还在调整，建议观察一段时间
   - 届时 `windowOptOutEdgeToEdgeEnforcement` 失效，需真正适配边到边

## 六、风险提示

**升级 targetSdk 是不可完全静态验证的改动**：

- 编译期只能确认代码能过，**看不出 UI 被遮挡、权限弹窗异常**这类运行时问题
- 本机当前 **无 adb 设备**，无法真机验证
- 建议：改完后至少在一台 Android 15+ 设备上验证
  - 设置界面布局是否正常（尤其状态栏/导航栏区域）
  - 蓝牙点显器能否正常连接
  - 权限弹窗是否变成按需请求

## 七、核查方法（可复用）

```bash
# 1. SDK 基线
grep -nE "compileSdk|targetSdk|minSdk" */build.gradle

# 2. 权限声明
grep -nE "uses-permission|usesPermissionFlags" brailleback/AndroidManifest.xml

# 3. 危险权限是否都有运行时请求
grep -rn "requestPermissions\|checkSelfPermission" */src

# 4. Android 13+ receiver 注册（漏 flag 会崩）
grep -rn -A3 "registerReceiver" */src     # 看是否有 RECEIVER_NOT_EXPORTED

# 5. 前台服务（targetSdk 34+ 必须声明类型）
grep -rn "startForeground" */src

# 6. 组件 exported（Android 12+ 强制）
grep -nE "<activity|<service|<receiver|exported" */AndroidManifest.xml
```
