## 为什么这样切

原文件把四类东西揉在一起：

1. **15 个教程步骤状态**（`Intro` … `TutorialFinished`），每个状态自己管视图加载、文案播报、手势/点位校验与下一步跳转；
2. **播报与触感反馈设施**（指令播报、事件读屏、手势震动、点位文案解析），被所有状态复用；
3. **输入/菜单/双击回调接线**，把底层 `BrailleInputView`、菜单对话框的事件转发给当前状态；
4. **视图生命周期与状态编排**（横竖屏重建、状态切换、脱离窗口清理、对外查询接口）。

切分原则是「一类东西一个文件，能一句话说清」，不按行数硬切：

- 步骤状态按**教程流程段落**分组：开场/校准一组、字母一组、手势一组、菜单/收尾一组。手势那组最多（7 个状态、504 非空行），但它们结构同构、共享同一套校验与动画调用，拆到一起比再按方向劈两半更内聚。
- 反馈设施与步骤解耦：它不持有步骤状态，只通过 `TutorialView` 暴露的内部成员读写视图与播报，因此写成同包扩展函数，沿用本仓库 `DisplayServiceConnectionFlow.kt`、`DefaultNavigationModeScrolling.kt` 已有的做法。
- 主文件保留回调接线与编排：这些代码直接持有视图实例、决定状态跳转时机，留在装配层最直接。

## 对外 API 与可见性的处理

- 对外类型与签名**一律未改**：`TutorialView` 类、嵌套接口 `TutorialView.TutorialState`（含 `State` 枚举）、`TutorialView.TutorialCallback`、构造参数、公开方法、伴生常量（`ROTATION_*`、`FREE_INTERACTIONS_MAX`、`AUDIAL_ANNOUNCEMENT_*`）保持原名原位。`BrailleIme.kt`、`KeyboardView.kt`、`AccessibilityOverlayKeyboardView.kt` 引用的限定名没有变化。
- 拆出去的状态类原来是内部 `inner class`，搬到同包后改为顶层类，构造时持有宿主 `TutorialView` 引用；类名保持不变。
- 为让同包扩展函数与新状态类访问宿主成员，一批原本 `private` 的字段/方法放宽为 `internal`（模块内可见，不对外暴露）：视图实例、当前状态、播报计数、`handler`、状态切换与播报/反馈方法等。`internal` 只在 `addon:brailleime` 模块内可见，不改变模块间 API。
- 既有警告（`Handler()` 构造 deprecation、回调参数名 `hand`/`calibration` 与超类不一致）按原样保留，没有顺手改签名。

1. **主文件预算**：`TutorialView.kt` 非空行 ≤ 700（拆后 434，留余量）；
2. **职责归属**：四个状态文件与反馈文件里必须能找到对应的类/扩展函数签名；
3. **反向断言（防回潮）**：主文件里不许再出现 `inner class Intro` 等 8 个步骤类声明，也不许再出现 `private fun speakAnnouncement(` 等 7 个反馈/播报方法实现；手势文案映射（`perform_hide_keyboard_announcement`）不许抄回主文件；

## 踩到的坑

- 顶层状态类通过宿主引用访问成员时，匿名 `UtteranceCompleteRunnable` 里的 `this` 指向回调对象而不是 `TutorialView`，方法引用要先把宿主收进局部变量再写 `host::onUtteranceCompleted`。
- 伴生常量在扩展函数里不能用裸名访问，需写成 `TutorialView.FREE_INTERACTIONS_MAX` 这种限定形式。
- 契约测试里「无构造参数」的 `TutorialFinished` 类签名不带括号，断言串要相应去掉 `(`，否则文本匹配不上。
