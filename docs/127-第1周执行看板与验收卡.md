## 2 四张验收卡

每张三段：用户能感知到什么 / 什么情况算失败 / 平移到产品的意义。不写实现细节，不指定包里放什么类。

### 验收卡 N1 · 转译体检单

- 用户能感知到什么：导出一份真实文档后，能听到一张分类朗读的清单，把没译出的字符、超宽的行、违反避头尾的位置、缩写过密的段落、末行孤字分别报出来；一次真实导出至少列出 3 类问题。
- 什么情况算失败：清单读不出来，或问题混在一起定位不到具体行和字；清单改动了导出正文；整份导出一个问题都报不出，而已知样本里明明存在问题。
- 平移到产品的意义：把「译得对不对」从靠手摸、靠运气抽查，变成每次导出自带一份可朗读的自查表；先给转译质量装上秤，再谈分词与排版优化。

### 验收卡 N3 · 打印预检

- 用户能感知到什么：送打印前先听到这份文件「可以打」还是「需要重排」；行宽越界、页数过多、装订边不足、点密度超限都会被单独指出。
- 什么情况算失败：该判重排的文件被判成可打，打到纸上才发现出界；预检直接去碰打印机或改动排版；所有文件一律回答「可打」，预检形同虚设。
- 平移到产品的意义：纸质盲文打印出错成本高，纸、点、时间都浪费；预检把问题拦在送印之前，让纸面交付先有一道闸。

### 验收卡 N4 · 桌面比对台

- 用户能感知到什么：在电脑上跑同一批句子，自研引擎与对照标准两边结果并列；不一致的句子单独列出，每句留出人工判定位置；第一批先跑通 50 句。
- 什么情况算失败：两边结果不并列，差异句混在全量里找不到；工具把差异直接判成「我们错」而不留人工判定；比对工具被打进 App 安装包；许可证边界没查清就落地。
- 平移到产品的意义：低成本找出两边口径分歧，给 N2 语料提供候选句，是把测试从「防重构」推向「防错译」的前置一步。注意：差异不等于我们错，必须人工判定；分流细则以 docs/131 为准。

### 验收卡 N2 · 真值对语料

- 用户能感知到什么：语料进回归后，再跑出错时能听到第一句出错的话和第一个差异格；整套语料一分钟内跑完；经存疑池抽检判定为我们真错的句子，能在回归里被稳定复现；至少抓出 5 个现存错译。
- 什么情况算失败：被判真错的句子在回归里复现不出来；差异定位不到句和格；跑完超过一分钟，拖慢每次收口；语料条目没有来源标记，工具判定、口径差、人工判定分不清；存疑池该上交人工的被工具直接判掉；攒不到 200 句有判定语料仍硬撑原路线。
- 平移到产品的意义：这是把现有用例从「防重构」升级成「防错译」的低成本路径，也是后面反向翻译、用户规则覆盖等功能的秤。三道筛口径、抽样比例与折算工作量以 docs/131 为准，本卡不重复设计。

## 3 已由团队决定的两次拍板

本节替换 126 §7 的两条待拍板事项。两条均已决定，团队不再自决反复；代价如实记下。

### 3.1 release 签名密钥

- 定了什么：本机新生成一套 release keystore；不沿用任何旧机器上的旧密钥。包名已独立、无历史包袱，新密钥一次定下来。
- 保管口径：keystore 与 keystore.properties 不进仓库，放仓库外；决定理由、生成参数、保管位置写进文档；密码只落在本机可读处，并提示产品负责人备份。
- 代价：装过旧签名包的设备不能直接覆盖安装，需要先卸载再装；新密钥从第一天起由本机保管，一旦丢失或换机，需要走密钥恢复流程才能发升级包。
- 谁执行：发布密钥专项，不在六角色表内，由 ENGINE 支撑。
- 证据落点：docs/133（决定理由、生成参数、保管位置）加仓库外密钥路径；密码不写入文档。
- 关联看板条：K-06、K-19。

### 3.2 N2 语料判定方式

- 定了什么：不做 500 句全人工判定；桌面比对台先筛差异，只把存疑项交用户抽检。
- 三道筛口径：
  1. 两边一致：标记为工具判定，入语料。
  2. 有差异但属已知口径差：标记为工具判定加口径差说明，入语料。
  3. 有差异且口径不明：进存疑池，交人工判定。
- 抽样比例与折算工作量：由 RESEARCH 在 docs/131 给出，本看板不另设数字。
- 代价：判定速度快，但工具筛掉的句子里理论上可能藏错；一致句与口径差句都带工具标记，后续抽检要能按标记回溯。
