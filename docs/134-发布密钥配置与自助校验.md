# 134 · 发布密钥配置与自助校验

> 日期：2026-11-26

> 本文记录**已落地的那份配置文件**：字段形状、校验命令、出错怎么查。口令一律不写进本文。

---

## 1 已落地的东西

主仓库根已有 `keystore.properties`（本机私有，**不入库**），四个字段：

- `storeFile=D:/keys/brailleback-release.jks`（正斜杠写法，Windows 下 Gradle 照样认，避免反斜杠被属性文件当转义符）
- `storePassword=`（24 位可打印 ASCII，与密码文本一致）
- `keyAlias=brailleback-release`
- `keyPassword=`（与 `storePassword` 相同，133 §2 已核过一致性）

配套文件：

- 密钥库：`D:\keys\brailleback-release.jks`（4402 字节，PKCS12，RSA 4096，有效期至 2054-04-13）
- 密码文本：`D:\keys\brailleback-release-密码.txt`

不入库的依据：`.gitignore` 第 76–78 行已有 `keystore.properties`、`*.jks`、`*.keystore`；`D:\keys` 在两个工作树路径之外，本身也不是 git 工作树。

---

## 2 为什么复用而不是新生成

已在 133 §1 定过，这里只补两条工程理由：

1. 手上 54.18 MB 那个包确由这把钥匙签过；换新钥匙等于把已签过的包判死，后续升级必须同签名才能覆盖安装。
2. AAA 级要求里唯一不可回收的东西就是签名身份。两把钥匙分治，日后排查「谁签的」成本会翻倍。

---

## 3 自助校验（三条命令，都可在本机照做）

**第一条：口令能不能开库**（不需要密码里任何字符暴露在外，命令里用 `$pw` 变量或粘贴输入）

```
keytool -list -keystore D:\keys\brailleback-release.jks -storetype PKCS12 -storepass <口令>
```

期望：`Keystore contains 1 entry`，条目名 `brailleback-release, PrivateKeyEntry`。本文落地时实测通过。

**第二条：证书指纹是否与 133 §4 一致**

```
keytool -list -v -keystore D:\keys\brailleback-release.jks -storetype PKCS12 -storepass <口令> | findstr /C:"SHA256"
```

期望：与 133 §4 记录的 SHA-256 前缀 `e0bf6b26…` 同一串。

**第三条：产物是不是这把钥匙签的**

```
apksigner verify --print-certs <apk路径>
```

期望：`Signer #1 certificate DN: CN=BrailleBack, OU=Braille Service, O=BrailleBack, C=CN`。若显示 `CN=Android Debug`，说明仍在用 debug 签名（主仓库当前 release 产物就是这种状态，见 133 §4）。

---

## 4 常见错法对照

- **`Keystore was tampered with, or password was incorrect`**：多半是 `storePassword` 与密码文本不一致，或属性文件里带了行尾空格。用 §3 第一条先确认口令本身能开库，再查文件。
- **`Failed to read key ... from store`**：`keyAlias` 拼错。本库只有一个条目，别名固定为 `brailleback-release`。
- **构建报 `keystore.properties` 找不到**：Gradle 侧按 `rootProject.file('keystore.properties')` 取，文件必须在**仓库根**，不是模块根。
- **签名成功但安装失败覆盖**：设备上已有 debug 签名的旧包，签名不同不能覆盖，需先卸载。

## 5 备份（仍未做，属产品负责人动作）

`D:\keys\brailleback-release.jks` 与 `D:\keys\brailleback-release-密码.txt` 分两份介质各存一份，其中一份离线。

- 备份时**必须成对**：只有 jks 没有口令，等于没有；只有口令没有 jks，也等于没有。
- 丢了不可恢复：这把钥匙签过的包以后无法再升级，只能换包名重新分发，用户数据与升级链全断。
- 建议顺序：先复制到 U 盘，再复制到另一台设备的加密目录，最后确认两份都能开库（回到 §3 第一条各跑一次）。
