# 85 - 稳定性债第 1、2 条：把「连着但不动」变成「自己断链重连」

- 日期：2026-11-25
- 依据：77 号文阶段 3 第 1、2 条；现场依据 11-13（USB 写超时后只能拔插）、54 号第 1 条（蓝牙读循环缺超时）

## 1. 两条债的共同点

连接状态显示「已连接」，硬件却不再响应。上层看到的只是「刷新停住」，没人去判死链，于是只能
拔插 USB 或重启，这就是 11-13 现象。

判据统一抽成纯 Kotlin 的 `LinkStallPolicy`，两条触发条件命中任一即判死：

| 条件 | 含义 |
|:---|:---|
| 连续写失败 ≥ 3 次 | 写入明确报错，通道已经不可用 |
| 有待写内容 且 距上次成功写入 ≥ 10 秒 | 回调丢了 / 写调用卡住（这才像「一直连着」的那种卡） |

`hasPendingWork = false` 时**不做**超时判定——屏没有新内容本来就不该写，空闲不等于死链。

## 2. USB / brltty 路径（`DriverThread`）

- 新增 `lastSuccessAt`、`consecutiveWriteFailures`，在 `writeWindowInternal()` 里成功清零、失败累加。
- 已有每 5 秒一条的遥测线程继续输出 `driver stats`（原样保留），**并在同一处做判定**：命中即
  打一行 `link declared dead: ... asking the service to reconnect`，再调 `initListener.onDriverFailed()`。
- 服务侧本来就在 `handleDriverFailed` 里走 `prepareAutomaticRetry`（既有退避重连），这一步不需要改。
- `driverFailureNotified` 是 `AtomicBoolean` 保证只报一次，避免重连过程中反复触发。
- 回调本身包了 try/catch：守护线程不能被一次回调异常带走，否则就再没人判死链了。

## 3. 蓝牙（无界 GATT，`WujieGattConnection`）

- Android BLE 栈一次只允许一个 GATT 操作，回调一丢，`mOpInFlight` 永远为 true，帧队列全卡死。
- 现在每个操作入队时都挂一根 4 秒计时绳（`mOpTimeout`）：超时即放弃该操作、清掉 in-flight 帧、
  重排队列继续走。
- 连续 3 次操作拿不到回调（`OP_TIMEOUTS_BEFORE_FAIL`）就判通道已死，`fail(ERROR_TIMEOUT)`，
  走既有 `scheduleAutoReconnectIfNeeded`。
- 只要收到一次回调就清零计数（`finishOpLocked`）——栈还活着就不该判死。
- 新增 `ERROR_TIMEOUT = -6` 与文案 `connprog_wujie_timeout`（中英各一份），失败原因不再只显示数字码。

## 4. 验证

- 新增 `LinkStallPolicyTest`（4 例）：只看连续失败能判死；有待写内容才判超时；空闲永不判死；
  阈值可配置且边界含等号。
- `:brailleback:testDebugUnitTest` 926 例全绿；`:brailleback:lintDebug`、`:service:lintDebug` 均 0 error；
  `assembleDebug` 成功并已装到手机（装包后确认无障碍服务仍在启用列表里）。

## 5. 待真机

- 这两条的真实验收只能在设备上做：USB 拔掉写测试、蓝牙远离/干扰造丢回调。
- 阈值（10 秒 / 4 秒 / 3 次）是先保守取的：真机上若出现「慢设备被判死」，只需调
  `LinkStallPolicy.DEFAULT_STALL_MILLIS` 与 `OP_TIMEOUT_MS`，判据本身不用改。
