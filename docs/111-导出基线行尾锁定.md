# 111 - 导出基线行尾锁定

> 日期：2026-11-26
> 起因：`BrailleExporterTest` 的黄金样本比对受 `core.autocrlf` 行尾归一影响，全新 checkout 会随机挂掉；本批用 `.gitattributes` 只锁 `.txt` 样本的行尾
> 结果：`.gitattributes` 一行规则锁定 `**/export_baseline/**/*.txt -text`；全新 detached worktree `3ff9ebe` 复测 972 用例 / 失败 0，`BrailleExporterTest` 21 / 0

## 问题现象

`BrailleExporterTest.readBaselineBytes()`（测试源码）直接 `readBytes()` 读资源做逐字节比对，**没有行尾归一**：

```kotlin
private fun readBaselineBytes(name: String): ByteArray {
    val stream = javaClass.getResourceAsStream("/export_baseline/$name")
        ?: throw AssertionError("基线缺失: $name")
    return stream.use { it.readBytes() }
}
```

三条基线比对口径：

- `sample.brf`：`assertBytesEquals(readBaselineBytes("sample.brf"), brf.content.toByteArray(US_ASCII))`，**逐字节**比对；
- `sample.brl`：按 UTF-8 字符串比对；
- `sample.txt`：按 UTF-8 字符串比对。

主仓库本地工作区里 `sample.txt` 早期落盘为 LF，靠这个偶然状态通过；一旦在 `core.autocrlf=true` 的机器上全新 checkout，Git 会把 `.txt` 的 LF 转成 CRLF 再写盘，`sample.txt` 由 **481 B（CR 0 / LF 28）** 变成 **509 B（CR 28 / LF 28）**，读出的基线多了 28 个 CR，字符串比对失败。

## 三个样本实测（主仓库 `3ff9ebe`）

| 样本 | 字节数 | CR 数 | LF 数 | 期望行尾 | 依赖 |
|:---|--:|--:|--:|:---|:---|
| `sample.txt` | **481** | **0** | 28 | LF | 本轮用 `-text` 锁死，不再被 autocrlf 转换 |
| `sample.brf` | **210** | **29** | 29 | CRLF | 靠 `autocrlf=true` 补 CR；**不能**锁成 `-text` |
| `sample.brl` | **511** | **29** | 29 | CRLF | 靠 `autocrlf=true` 补 CR；**不能**锁成 `-text` |

## 为什么只锁 `.txt`，不整目录 `-text`

`.brf` / `.brl` 两条黄金样本的期望内容本身就是 **CRLF**（各 29 个 CR / 29 个 LF），当前工作区的 CR 是 `core.autocrlf=true` 在 checkout 时补上去的；导出器产出的 BRF 内容同样以 `\r\n` 换行（见 `brfUsesCrlfAndNoBareLf` 用例）。

如果对整个 `export_baseline/` 目录加 `-text`：

1. `.brf/.brl` 的 CR 会被去掉、落成 LF，基线变成无 CR；而比对目标 BRF 内容带 CR，两条都会挂；
2. 反过来若只锁 `.txt`，`.brf/.brl` 继续走 autocrlf 的既有行为，与基线期望一致。

两种错法都实测过：整目录 `-text` 会把 `.brf/.brl` 两条比对弄挂，因此规则只落到 `*.txt`。`.gitattributes` 全文仅一行：

```gitattributes
**/export_baseline/**/*.txt -text
```

## 残余脆弱点（只记录，不修）

- 在 `core.autocrlf=false` 的机器上 checkout 时，`.brf/.brl` 会落成 LF（缺 CR），那两条比对仍然会挂；本轮规则只覆盖了 `.txt` 这一侧。
- 彻底修法：把 `.brf` / `.brl` 两个 golden 以 **CRLF 形态固化进 blob**（提交字节里直接带 CR），不再依赖 checkout 时的 autocrlf 补行尾；这会改动基线文件的提交字节，需同步重跑 `BrailleExporterTest` 核对期望值，本批未做。
