# 36 · 界面层协程化（第一批：只剩三处值得改）

> 2026-11-18。承 [34-线程与Handler盘点](./34-线程与Handler盘点.md) 的结论做第一批落地。
> 前提不变：**盲文驱动链不协程化**（brltty 阻塞式 C 驱动 + 同步 bulk transfer +
> 插拔重建线程），所以「协程架构」能动的只有界面层与少量纯定时逻辑。

## 1. 盘点结果：113 行命中里真正能动的只有三处

按 `Handler(` / `postDelayed` / `removeCallbacks` / `HandlerThread` 全仓搜索，
24 个文件 113 行命中。逐点判类后：

| 类别 | 代表 | 结论 |
|:--|:--|:--|
| 驱动链 | `DriverThread`、`UsbDisplayConnection`、`HidDisplayConnection`、`WujieGattConnection`、`DisplayManager` | **不动**，理由见 docs/34 |
| View 级高亮清除 | `BrailleView.highlightCell()` 的 `postDelayed(mClearHighlightedCell, 600ms)` | **不动**：`View.postDelayed` 随 attach/detach 走，换协程反而要自己管 scope |
| 手势时序对齐 | `DraggableOverlay` 的 `sendMessageAtTime(MSG_LONG_PRESS, event, event.eventTime + 700ms)` | **不动**：要按 `MotionEvent.eventTime` 对齐，`delay()` 会丢事件时间基准 |
| IPC / 线程间回调落点 | `OverlayDisplay` 的 `MainThreadHandler` / `DisplayThreadHandler`、`BrailleBackService` 的 `removeCallbacks`、`DisplayServiceHandler` | **不动**：Handler 本身就是这两条线程的汇合点 |
| 服务级单次延迟 | `BrailleImeHostBridge` 的朗读节流、`PassthroughProbe` 的 auto-disarm、`DefaultNavigationMode` 的主线程 Handler | 留到下一批（都在服务生命周期里，改它们要连带管服务销毁） |
| **界面层定时器** | `OverlayTutorialActivity`、`IMESetupWizardActivity` | **本批改了** |

（补充：`BrailleDisplayScreen.kt` / `DeveloperOptionsScreen.kt` 里的「Handler 命中」是
假阳性——命中的是 `androidx.activity.compose.BackHandler`，这两个屏没有真的 Handler。）

## 2. 改了什么

### 2.1 `OverlayTutorialActivity`：两个自调度 Runnable → 两个协程循环

原来每拍在 `run()` 末尾再 `postDelayed` 自己，`onResume` 起、`onPause` 用
`removeCallbacks` 配对取消；`Runnable` 活在成员字段里，页面销毁后仍可能排着一拍。

现在：

```kotlin
mPanDemoJob = lifecycleScope.launch {
    while (isActive) { /* 翻转左右按钮的按下态 */; delay(PAN_DEMO_INTERVAL) }
}
mRoutingKeyDemoJob = lifecycleScope.launch {
    while (isActive) { /* 随机点亮一格 */; delay(ROUTING_KEY_DEMO_INTERVAL) }
}
// onPause(): 两个 job 各自 cancel
```

- 间隔不变：`PAN_DEMO_INTERVAL = 500ms`、`ROUTING_KEY_DEMO_INTERVAL = 1500ms`；
- 起手第一拍立即执行，与原 `post(...)` 行为一致；
- 基类从 `android.app.Activity` 换成 `androidx.activity.ComponentActivity`
  （要拿 `lifecycleScope` 就得是 `LifecycleOwner`）。它没有自定义主题约束
  （沿用 manifest 里的默认主题），不像前几批的 `BraillebackTheme` 需要绕开 AppCompat；
- 顺手删了只写不读的 `mPanDemo` 字段。

### 2.2 `IMESetupWizardActivity`：300ms 自建 Handler → 宿主 Activity 的 lifecycleScope

原来 `DefaultBrailleImeFragment.onResume()` 里 `val handler = Handler()` 只为排一次
`postDelayed({ imm?.showInputMethodPicker() }, 300L)`（等系统把 UID 认对）。

现在挂到宿主 Activity 的作用域：

```kotlin
val host = activity as? ComponentActivity ?: return
host.lifecycleScope.launch { delay(INPUT_METHOD_PICKER_DELAY_MS); inputMethodManager?.showInputMethodPicker() }
```

这个 Fragment 是 `class ... : Fragment()` 的**嵌套类**（不是 inner），拿不到外部
`this@IMESetupWizardActivity`；而 `android.app.Fragment` 本身不是 `LifecycleOwner`，
所以只能取宿主的 scope。300 这个数字抽成了 `INPUT_METHOD_PICKER_DELAY_MS` 常量。

**保留的那一个 Handler**：`ContentObserver(handler)`——`ContentObserver` 的构造参数
要求 `Handler`（决定回调落到哪个 Looper），属 API 硬约束。已加注释说明它只服务于
这个观察者，并在契约测试里钉住「本文件只允许这一个 `Handler()`」。

## 3. 新增的两道门

### 3.1 `CoroutineScopeContractTest`（4 例，JVM 单测）

| 用例 | 断言 |
|:--|:--|
| `activitiesDoNotScheduleDelayedWorkWithBareHandler` | `brailleback/src` 下所有 `*Activity.kt` 不含 `postDelayed(` |
| `overlayTutorialDemosRunInLifecycleScope` | 基类是 `ComponentActivity`；两个 job 都挂在 `lifecycleScope`；两个 `delay(常量)` 还在；`onPause` 有 `cancel()`；`object : Runnable` 已消失 |
| `imeWizardPickerDelayRunsInHostActivityScope` | 常量 `INPUT_METHOD_PICKER_DELAY_MS = 300L`；走 `delay(...)`；是 `activity as? ComponentActivity` 的 scope |
| `imeWizardHandlerSurvivesOnlyForContentObserver` | 文件里 `Handler()` 恰好 1 处，且被 `ContentObserver(handler)` 使用 |

为什么值得钉：这类「自建 Handler 排延迟」不是编译错误，lint 默认也不抓；出问题的
表现是页面销毁后还弹一次选择器/闪一下，只有静态契约能防回退。

### 3.2 `OverlayTutorialSmokeTest`（3 例，仪器测试）

| 用例 | 证明什么 |
|:--|:--|
| `overlayTutorialReachesResumed` | 页面能起、演示跑 1.5 秒不带崩 |
| `panDemoTogglesWhileResumed` | 1.2 秒内采样 4 次，按钮按下态确实在翻转（协程真的在跑） |
| `demoTimersStopWhenPaused` | `moveToState(CREATED)` 之后 800ms 按钮状态不变（`onPause` 的 cancel 真的生效） |

第三条是这次改动的核心价值：静态契约只能证明「写法变了」，证明不了「暂停后确实停了」。

## 5. 没做 / 下一批候选

- `BrailleView`、`DraggableOverlay`：已判定不动（见第 1 节），不是遗漏；
- 服务级三处（`BrailleImeHostBridge` 朗读节流、`PassthroughProbe` auto-disarm、
  `DefaultNavigationMode` 主线程 Handler）：都在服务生命周期里，改动要连带处理
  服务销毁/重连的取消语义，单独一批做；
- 驱动链的「几十秒停更」问题仍未解：那是 native brltty 的 1000ms 传输超时，
  应用层没有超时常量与失败恢复，与协程无关，要另开一条线。
