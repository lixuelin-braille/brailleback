## 1. 真机证据（引自 117 §9，数字不重算）

> 以下为用户在真机（小米 24117RK2CC，`10.121.61.209:5555`，versionCode 34）实测回传，本机未对真机发任何 adb 命令；原文在 117 §9.2 / §9.3，本节只引用不改写。

- 样本：**1,545,748 字符**大书；`dumpsys gfxinfo` 累计 **1402 帧**。
- Janky（deadline 口径）**21.9%**；Janky（>16.7ms legacy）**49.1%**。
- P50 / P90 / P95 / P99：**12 / 85 / 93 / 150 ms**。
- `Slow UI thread` **266 帧**；`Missed Vsync` **122**；`High input latency` **1271**。
- GPU P50 / P90 / P99：**2 / 10 / 13 ms**。
- 主观：翻译推进期「隔几秒顿一下」，翻译完成后不卡。
- 真机日志：`page table: unit=900 pages=N` 每 **1.4–2.8 秒**重建一次，pages `813→932→1045…→3157`；同期 `append: +N` 与续装插段也在主线程。

### 1.1 与 116 结论的环境差异

- 116 在模拟器上把长帧拆到帧内阶段，结论是「长帧压 GPU（光栅/提交）段」；该结论**只对模拟器 swiftshader / host GL 回环成立**（116 §4.2/§4.3：B 组长帧 GPU 主导 55.6%、A 组 96.7%）。
- 真机口径相反：GPU P50/P90/P99 仅 2/10/13 ms，几乎空闲；长帧压在**主线程**（`Slow UI thread 266`）。两套环境的瓶颈段不同，不能拿 116 的 GPU 归因外推真机；真机以 117 §9.2 为准。
- 模拟器 host 是 GL 翻译层回环（116 §3 保留意见），复现不出真机的 CPU 主线程量级；本轮因果测量以**设备无关的单次重建耗时表**为准（§3），gfx 百分位只作旁证。

## 2. 代码级因果链（源码复核，基线 `4fd7487`）

复核结论与用户给出的定位一致，落点如下：

1. `ReaderTranslation.appendBrailleStream(deltaText, deltaCells)`：每追加一块翻译流就调 `rebuildPageOffsets(keepPosition = true)`（`ReaderTranslation.kt:31`），随后 `showPage(resetScroll = false)` 并打 `append:` 日志。
2. `ReaderPageNavigator.rebuildPageOffsets(keepPosition)`：无条件 `mPageOffsets = BrailleFileDecoder.pageOffsets(mStream, readingUnit())`（`ReaderPageNavigator.kt:93`），没有「流只变长、旧表可续」的分支。
3. `BrailleFileDecoder.pageOffsets(stream, unit)`：从 `off=0` 起 `while (off < stream.length) { out.add(off); off = nextOffset(...) }`（`BrailleFileDecoder.kt:683`），每页做词首/边界对齐；**每次都从第 0 字符走到流末尾**。
4. 因果链：翻译每 publish 一块（真机 1.4–2.8 秒一次）→ 主线程整表重算一遍当时已翻出的全部页数（真机 3157 页 / 约 264 万字符）→ 长帧计入 `Slow UI thread`；翻译结束后不再 publish，重建停止，故「完成后不卡」。

其余 rebuild 调用方本轮保持整表不动（用户明确先不改）：`ReaderFileLoader` 打开文件、`onScreenTextMetrics`（转屏/换字号）、`restorePendingOffsetIfReached`（续装恢复）、点显器连接/方数变化。

- 真机样本 1,545,748 字符；模拟器大书 614,489 源字符 / 1.99M 盲文流，两者段落数、publish 块大小不同，帧数与毫秒不可直接对标。

## 4. 第 1 步：增量重建（已采用，单独提交 `e3df42f`）

### 4.1 改动

- `BrailleFileDecoder.appendPageOffsets(stream, unit, existing)`：从 `existing.last()` 起按 `nextOffset` 继续走到新 `stream.length`，返回「旧表 + 新增项」，**已有映射一字不动**。回落整表重建的情形：流为空、旧表为空、旧表末位 ≥ 新流长度（截短/换书）；`next <= off` 步进不动时防死锁跳出。
- `ReaderPageNavigator` 新增 `rebuildPageOffsetsIncremental(keepPosition = true)`：先校验建表时的 unit 与当前 unit 一致（新字段 `mPageUnit`，不再每页现算）；一致才增量，不一致（转屏、换字号、点显器方数变化）回落整表重建。整表入口 `rebuildPageOffsets` 同步刷新 `mPageUnit`。
- `appendBrailleStream` 追加块改调增量版；打开文件、`onScreenTextMetrics`、`restorePendingOffsetIfReached`、点显器连接变化**仍走整表**。
- 日志格式不变：`page table: unit=… pages=… connected=… displayCells=… keep=…`，既有取证脚本按 tag/文案解析不受影响。
- 失败回退路径（`restoreProgress` 清空进度）同步复位 `mPageUnit = -1`。

### 4.4 单测

- 新文件：`brailleback/src/test/kotlin/com/linxi/brailleback/PageOffsetsIncrementalTest.kt`（纯 JVM，无 Android/Compose 依赖）。
- **新增 6 条用例**：
  1. 随机流 × 4 个 unit（40 / 120 / 337 / 752）× 4 组随机种子 × 三段连续追加，增量表与整表 `pageOffsets` **逐项相等**（`assertArrayEquals`）；

## 5. 第 2 步：重建移出主线程（本轮不采用）

- 原方案：页表计算走后台协程（`Dispatchers.Default`），主线程只做一次快照替换；连续追加时按流长度 / 版本号丢弃过期结果，禁止旧结果覆盖新流。
- 评估：第 1 步已消除 O(全书) 重复扫描，残留主线程工作量与本次追加块同量级——而追加块的文本拼接、`CellSourceTable` 挂接、`showPage` 重组本来就在主线程付这笔钱。后台化引入 stream 版本快照、过期结果丢弃、表与偏移一致性等新竞态面，当前证据不支持再加这套复杂度。
- 结论：**本轮不做、不提交**。触发再评估的条件：真机复验翻译推进期仍有 >16.7ms 长帧、且帧内拆解显示页表重建（而非追加重组/续装插段）仍是主线程主要占比。

## 6. 第 3 步：翻译期不实时推总页数（本轮不采用）

- 原方案：页码标签 / 滑块的 `pageCount` 只在显式翻页或翻译告一段落时刷新，避免每约 2 秒涨一次触发滑块与文案重组。
- 评估：本轮测量没有抓到 `pageCount` 刷新构成独立热点的证据；改 `scrollState.pageCount` 更新时机需要额外保证「第 N 页 共 M 页」在翻页时仍准确，并回归两个契约测试。按红线，收益在噪声内或影响读数准确性时如实写「不采用」并回退。
- 结论：**本轮不改、不提交**；未动 `ScrubberBar` 语义块、未动 `scrollState.pageCount` 更新路径。
