# 51 · 盲文表补全：72 → 122 张，36 种新语言可用

> 本轮口径：本项目里「盲文表」= liblouis 翻译表（`service/res/raw/translationtables.zip`
> + `service/res/xml/tablelist.xml`）。先把「补全」到底缺什么量出来，再补。

## 一、先量：缺的到底是字符还是表

对 `service/jni/liblouiswrapper/liblouis/tables` 下 485 个文件、`zhcn-cbs-full.ctb` 与其
include 闭包做了逐码位统计：

| 区段 | 总数 | zhcn-cbs.ctb | zhcn-cbs-full.ctb | zh-chn.ctb |
|:---|---:|---:|---:|---:|
| CJK 基本区 4E00–9FFF | 20,992 | 7,191 | **20,796** | 20,796 |
| CJK 扩展 A 3400–4DBF | 6,592 | 0 | 0 | 123 |
| 常用标点 3000–303F | 64 | 7 | 7 | 7 |
| 全角 FF00–FFEF | 240 | 7 | 7 | 7 |

**结论一：汉字不需要补。** 基本区覆盖 20,796/20,992，缺的 196 个里
106 个是 GBK 内、90 个在 GBK 之外（U+9FA6–9FFF）。逐个看是韩日专用汉字
（`乤 乥 乫 匁 唜 唟 嗧` 一类），中文语料里不出现，补了也无人读。

**结论二：标点不需要补。** 按 include 闭包核对 60 个常用中文标点/全角字符
（`，。！？；：、（）《》〈〉“”‘’「」『』【】〔〕—…·～０-９ＡＺａｚ`），闭包已定义
22,109 个码位，**60/60 全部有定义**。`zhcn-cbs-full.ctb` 头部 include 了
`braille-patterns.cti` + `en-ueb-chardefs.uti` + `en-ueb-math.ctb` + `en-ueb-g1.ctb`，
全角与 ASCII 标点由后两者提供。

**结论三：真正的缺口在「表清单」，不在字符。**

| 口径 | 数量 |
|:---|---:|
| tables 目录里的文件 | 485（17.5 MB） |
| 可直接当翻译表用的 `.ctb/.utb` | 253 |
| 清单 `tablelist.xml` 登记 | **67 个唯一文件 / 72 个条目** |
| 打进 `translationtables.zip` 的文件 | 143（含 include 依赖） |

也就是说：**上游 liblouis 早就把表写好了，只是这个 App 没登记、没打包**。
用户能选到的语言，只有 34 种。

## 三、刻意不补的三类（都有理由，不是漏）

1. **印度语系 `*-in-g1.utb` 薄壳表**（`as-in / be-in / br-in / gu-in / ka-in / kh-in /
   ks-in / ml-in / mn-in / mr-in / np-in / or-in / pu-in / sa-in / si-in / te-in`）。
   这批文件都只有约 1.2 KB，是挂 `en-in-g1` 骨架的壳。登记进清单等于告诉用户
   「这里有孟加拉语/古吉拉特语」，点进去却是英文骨架规则，比不提供更糟。
   要补得等上游出真正的印度语输出表。
2. **日语**：仓库里只有 `ja-kantenji*.utb`（汉字直读 Kantenji）与 `ja-rokutenkanji.utb`，
   没有假名盲文表。Kantenji 的价值在汉字读音检索，且其中两张合计 500 KB，
   单独一批再评估。
3. **学术/死语言**：`akk`（阿卡德语）、`cop`（科普特语）、`grc`（古希腊语）、
   `hbo`、`syc`、`uga`、`gez`、`ovd`、`smi`、`sah`、`cuneiform*`、`IPA`。
   进了清单只会让语言列表变长，没有任何用户会选。

## 四、打包：把「脚本跑不了」变成「离线可跑」

原 `service/tables/mktranslationtables.sh` 依赖 bash + python（`copywithdeps.py`）。
本机只有 `py.exe`，且 CI 也不一定装 bash，所以新增 PowerShell 版实现，**闭包算法一致**：

`tools/table-list/add-tables.ps1`
1. 校验 50 个新 id 不与现有冲突、文件真实存在；
2. 从每张登记表出发解析 `include` 链，递归收集依赖（`.cti/.uti/.dic` 一并带上）；
3. 闭包里任何文件缺失直接抛错（不许产出半残的包）；
4. 按 `liblouis/tables/<name>` 前缀重打 zip，压缩级别 Optimal。

实测：zip 2.26 MB → **2.48 MB**，条目 143 → **200 个文件**。
体积只涨 0.22 MB，因为新增表多数在 1–10 KB（最大的 `lo-g1.utb` 151 KB、
`ms-my-g2.ctb` 150 KB、`my-g2.ctb` 123 KB），且 liblouis 表文本压缩率极高。

## 五、契约测试：新增 4 条不变量

`service/src/test/.../translate/TableArchiveContractTest.kt`

| 用例 | 锁什么 | 失败意味着 |
|:---|:---|:---|
| `everyRegisteredTableShipsInTheArchive` | 清单里每个 `fileName` 都在 zip 内 | 界面上能选中、运行期加载失败 |
| `everyRegisteredTableHasItsFullIncludeClosureInTheArchive` | include 闭包全部在包内（递归） | 表能打开但规则缺依赖，输出残缺 |
| `archiveEntriesAllLiveUnderThePrefixLiblouisReads` | zip 条目必须以 `liblouis/tables/` 开头 | 解包路径不匹配，liblouis 找不到表 |
| `everyTableIdAndLocaleIsUsableByTheCatalog` | id 唯一、locale 匹配 `ll`/`ll_CC`、八点表不得带 grade | `TableList` 解析期抛 RuntimeException，整个表清单加载失败 |

前三条是针对「假生效」的：盲用户选了一个语言、点显器没反应，无法自查，
只能以为「这个语言不支持」。这三条把这种失败挡在构建期。

同时更新了 4 处写死的数量断言（语义不变，只是数字跟着数据走）：

- `BrailleCodeCatalogTest`：方案数 72 → 122、八点方案 25 → 26、id 去重 72 → 122
- `BrailleDisplayContractTest`：清单条目 72 → 122、分组后条目 72 → 122、语言组数 34 → 70

验证：**brailleback 56 套件 / 567 用例 / 0 失败；service 28 套件 / 187 用例 / 0 失败**
（合计 84 套件 / 754 用例，新增 4 条）。
