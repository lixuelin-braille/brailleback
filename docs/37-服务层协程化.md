# 37 · 服务层协程化（第二批：桥接层的延迟与探针）

> 2026-11-18。承 [36-界面层协程化](./36-界面层协程化.md)，做第二批：
> 把服务生命周期里那几拍延迟从自建 Handler 换成可取消的作用域。
> 这一批不只是风格统一——两处都顺手关掉了原来漏掉的取消窗口。

## 1. 改了什么

### 1.1 `BrailleImeHostBridge`：一个 `mainScope` 管三种延迟

原来 `private val mainHandler = Handler(Looper.getMainLooper())` 排三处延迟：

| 位置 | 用途 | 现在 |
|:--|:--|:--|
| `speak()` 里 `delayMs > 0` 且走无障碍公告 | 把公告交给外部读屏朗读 | `mainScope.launch { delay(delayMs); ... }` |
| `speak()` 里 `delayMs > 0` 且走自带 TTS | 字符反馈节流 | 同上 |
| `applyTouchExplorationPassthrough()` 的 150ms | 等 `setServiceInfo` 在系统侧生效再设直通区 | `passthroughApplyJob`，重设前先 cancel |

```kotlin
private val mainScope = CoroutineScope(SupervisorJob() + Dispatchers.Main.immediate)
fun shutdown() {
    mainScope.cancel()   // 先撤延迟
    // …再 stop/shutdown TTS、关 FeedbackController
}
```

**顺带修掉的隐患**：原来 `shutdown()` 完全不碰那个 Handler。服务销毁后在排的那一拍
仍会执行——往已经 `shutdown()` 的 TTS 里 `speak()`，或者对着已解绑的服务设直通区。
现在 `shutdown()` 第一句就是 `cancel()`。

另外把 `announce` 从 `Runnable` 改成局部 lambda，`sendAnnouncementEvent()` 成功时
不再需要 `return@Runnable` 这种标签跳转。

### 1.2 `PassthroughProbe`：作用域随 `install` / `uninstall`

原来这个单例里两个延迟（400ms 落地、180s 自动撤销）配一个 `autoDisarm: Runnable?`，
只有自动撤销那拍能取消：

```kotlin
fun uninstall(service: AccessibilityService) {
    // …
    if (armed) disarm(service, "uninstall")
    settleJob?.cancel(); settleJob = null      // ← 新补的
    autoDisarmJob?.cancel(); autoDisarmJob = null
    scope?.cancel(); scope = null
}
```

现在 `scope` 在 `install()` 里建立、`uninstall()` 里取消，两个延迟各有一个 Job 句柄。

**顺带修掉的隐患**：`uninstall` 原来只撤自动撤销那拍，**400ms 落地拍会漏**——
服务已经解绑了还去调一次 `setTouchExplorationPassthroughRegion()`。探针属于实验代码，
但它碰的是「全屏直通」这种能让读屏整屏失效的 API，漏一拍代价不小。

自动撤销那拍的写法有个细节：先 `autoDisarmJob = null` 再 `disarm()`，
否则 `disarm()` 会取消掉正在执行自己的那个 Job。

## 2. 刻意没改的

`DefaultNavigationModeScrolling.updateAfterScroll()` 里还有一个
`mMainHandler.postDelayed`——那是**滚动后按递增间隔轮询内容是否真的动了**的重试循环
（`SCROLL_UPDATE_DELAYS_MS[attempt]`，最多几拍，递归到内容移动或次数用尽）。

不改的理由：
- 它已经有等价的取消机制：`onDeactivate()` 把 `mScrollSequence` 加一，回调里
  `if (sequence != mScrollSequence) return` 直接丢弃，行为上等于取消；
- 回调里夹着 `AccessibilityNodeInfoCompat.recycle()` 的配对，改结构容易漏回收；
- 收益只是写法统一，不带来正确性改进。

## 3. 依赖

给 `brailleback/build.gradle` 补了 `implementation libs.kotlinx.coroutines.android`。

之前是**碰巧能编**：`lifecycle-runtime-android` / Compose 把 `kotlinx-coroutines-core`
传递带了进来，`launch`/`delay` 恰好可见；但 `Dispatchers.Main` 实际由
`kotlinx-coroutines-android` 提供，主源码直接用它就得直接声明。
版本沿用目录里的 `coroutines = "1.9.0"`（本机 `D:\cache\gradle` 缓存有该版本）。

## 5. 测试缺口（要说清的）

这两处改动的**运行时行为没有直接用例覆盖**：验证它们得启用无障碍服务
（`BrailleImeHostBridge` 只有键盘接上才走，`PassthroughProbe` 只有服务连上才 `install`），
而服务初始化会碰 `BrlttyWrapper`，在 x86_64 模拟器上必然 `UnsatisfiedLinkError`。
所以本批的保障是：静态契约（写法不许回退）+ 既有 172 例 service 单测 + 14 例仪器测试回归。
要真正测「服务销毁后不再说话/不再设直通区」，需要一次真机验证。
