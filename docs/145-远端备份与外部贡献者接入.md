## 2 为什么 main 会落后 61 个提交

一句话：**合并发生在本地，推送只发生在分支。**

- 每一轮收口都是把功能分支合进本地 `main`（`--no-ff` 合并提交）。
- 收口后只推了功能分支，`main` 不动——大概是因为早期定的规矩是「一律不 push」，把「备份」和「改写风险」当成了一件事。
- 结果：远端 main 停在 `61c7a6c`，本地已经走到 `72bb40c`。功能分支推了也没用——它们的内容没进 main，别人 clone main 拿到的还是 11 月 26 日之前的东西。

教训写成规则（126 §2.2）：**每轮收口推一次 main + 打锚点 tag**。备份价值在 main 上，不在分支上。

## 3 三条通给外部贡献者的路，按可行性排

### ① 补丁文件（最可行，推荐默认）

对方在自己机器上写完，导出一个补丁文件发过来，我们 `git am` 收进仓库。**作者信息自动保留**，不需要给仓库权限。

对方侧：

```
git config user.name  "对方姓名"
git config user.email "对方邮箱"
git format-patch -1 HEAD --stdout > my-fix.patch
```

我们侧：

```
git am my-fix.patch          # 保留原作者与提交信息
git log -1 --format='%an <%ae>'   # 核对作者对不对
```

只有一个提交时也可以更简单：`git diff > my-fix.diff` 发过来，我们手动 `git apply` 再自己写提交信息（这样作者信息会变成我们，**所以更推荐 `format-patch`**）。

优点：不需要账号、不需要网络权限、不涉及仓库所有权。
缺点：来回一轮、冲突要人工处理。

### ② Gitee 镜像后提 PR（国内可达，适合常态化协作）

Gitee 用手机号就能注册，国内直连速度快。把仓库镜像到 Gitee，对方在 Gitee 上 fork + 提 PR，我们审核后拉回来。

- 优点：有正经的 PR 界面、代码评审、CI 挂得上；国内网络无障碍。
- 缺点：要维护一个镜像的同步节奏（GitHub ↔ Gitee 双向容易乱），得定「谁是权威」——**权威只能是 GitHub**，Gitee 单向镜像。
- 前提：对方愿意注册 Gitee。

### ③ GitHub 加协作者（不推荐）

需要对方有 GitHub 账号且网络能到 github.com。既然这台机器匿名 HTTPS 都不通，能稳定用 GitHub 的外部贡献者本身就少。
仅在「对方本来就是 GitHub 活跃用户、而且愿意走 SSH」时考虑。给协作者写权限风险也最大：**一旦给了写权限，对方就能改写我们的历史**。

## 4 一个已实测的坑

**这台机器匿名 HTTPS 到 github.com 不通。** 实测 `curl` 走 SSL 失败、耗时约 24 秒后放弃；仓库本身走的是 22 端口 SSH，能正常工作。

所以以下这条路走不通，不要再试：

```
git clone https://github.com/lixuelin-braille/brailleback.git   # 此机上会失败
```

给外部贡献者的实际选择只有两个：

1. **SSH**：对方自己配置 SSH key（`git clone git@github.com:...`），前提是对方网络能到 22 端口；
2. **压缩包**：把仓库打成 zip 给对方（`git archive` 或直接压缩工作目录），对方解压后改、导出补丁发回来。这条路完全不依赖网络，适合完全没账号的人。

---

## 5 与外部贡献者协作时必须守住的三条

1. **四条红线不许碰**：盲文输出正确性、断连恢复、TalkBack 朗读语义、已支持点显器兼容性。碰了用户当天就没法用手机。
2. **禁入区**：`keymap/`、`ime/`、`DisplayManager` 内部逻辑；brltty 上游代码只许加包装层，不许改上游。
3. **四道门禁必须自己跑过再交**：构建、双模块单测、双模块 lint、模拟器冒烟。跑不过的补丁我们不收——不是不信任，是这台机器上没法替他验。

具体操作写在仓库根的 `CONTRIBUTING.md` 里，可以直接发给对方。
