# 15 · 运行时并发迁移清单（DisplayManager）

> 2026-11-15。针对 `brailleback/src/.../brailleback/DisplayManager.kt`（1527 行）。
> 目标不是「换框架」，是把 **Handler 消息队列 + volatile 字段**换成
> **单线程 confined 状态 + 结构化取消 + 可注入出口**，让核心刷新链路能在 JVM 里被测到。
> 现状：主运行时已是 Kotlin（118 个 `.kt` / 27,691 行，Java 仅 634 行），
> 但 `suspend fun` 为 0 个，本文件内 `@Volatile` 20 个。

## 一、现状线程模型

```
Display 回调线程（service/display 内部）
   │ onConnectionStateChanged / onInputEvent          （767 / 782 行）
   ▼
CallbackHandler（主线程 Handler，WeakReference 持 manager）   （1076 行起）
   ▲
   │ 交付内容、归还 Content、连接状态、输入事件
   │
DisplayHandler（HandlerThread "DisplayManager"）             （622–631、860–1028 行）
   │ 单线程串行消费：MSG_SET_CONTENT / RETRANSLATE / PULSE / STOP
   ▼
display?.displayDots(...)（DisplayClient / AIDL → :service 进程）

DisplayStats（独立守护 Thread，5 s 一次）                      （555–577 行）
   └ 刻意独立：handler 线程卡死时仍要出日志，用来区分「上层不刷新」与「线程被卡住」
```

关键常量（1647–1672 行）：`BLINK_OFF 800` / `BLINK_ON 600` / `MOTION_DEBOUNCE 350` /
`CONTENT_MIN_INTERVAL 250` / `MSG_SET_CONTENT=1` / `RETRANSLATE=2` / `PULSE=3` / `STOP=4`。

### 明确不迁

- `DisplayClient` / 20 个 AIDL：跨进程 ABI，含 `SelfBrailleService` 对外公开接口。
- brltty / liblouis 的 JNI 回调线程：C 侧决定线程，Java 侧只能接。
- `OverlayDisplay` 的 View 创建线程（`onLooperPrepared` 里构造）与 `CallbackHandler` 的 `WeakReference` 语义。
- `addon/*` 的 197 个 Java 文件：TalkBack 移植层，保持 Java 才能整文件同步上游。

    fun displayDots(dots: ByteArray, text: CharSequence, positions: IntArray?)

批 3 上半的实际做法（`DisplayRuntimeState.kt`）：五个跨线程布尔
（`connected` / `simulated` / `frozen` / `motionMode` / `cursorDots`）收进一个
不可变 data class，`refreshDecision()` 从同一份快照算裁决；`DisplayManager` 里

访问器。

这才是那次重构真正修掉的东西：`refresh()` 原来连读三个独立 `@Volatile`，
只保证单次读写可见，不保证三次来自同一时刻 —— 回调线程刚把 `connected` 置 true、
display 线程读到旧的 `frozen`，就会算出「已连接但暂停」这种当次不成立的决定
（表现为该刷的一帧被吃掉）。现在裁决只取一次 `runtimeState.value`。


批 2 的实际写法（`DisplayTimers.kt`）：`Debouncer` / `RepeatingTimer` / `OneShotTimer`
三个原语，调度器由调用方注入——生产环境是
`Handler(displayLooper).asCoroutineDispatcher()`（注意 1.7.3 只有 `Handler` 的扩展，
没有 `Looper` 的），测试里是 `runTest` 的 `backgroundScope`。

两个踩过的坑记在这里：

1. `OneShotTimer` 执行动作前必须先把 `job` 置空，否则动作内部（`doRefresh`）再排下一次时
   会以为自己还在排队而跳过，闪烁链断在第一次。
2. `runTest.advanceTimeBy(n)` 不会执行“恰好排在 currentTime + n”的任务，断言要么留 1 ms 余量，
   要么就别赌边界。

拆分后累计：`DisplayManager.kt` 1527 → 1185 行（非空 1095），`@Volatile` 21 → 10 个，
拆分出 6 个文件，测试 463 → 497 用例。

前两刀的 Kotlin 化要点：

- `Content` 的 `constructor()` + `constructor(textArg)` 合并为
  `@JvmOverloads constructor(text: CharSequence? = null)`，调用方零改动。
- `DisplayCallbackHandler` 虽然独立成文件，**仍用 `WeakReference`**：主线程
  队列持有 Handler，强引用管理器等于把无障碍服务一起泄漏。为此只把 4 个成员
  放宽到 `internal`，而不是用构造参数把管理器传进去。

`DisplaySplitContractTest` 卡住的结构底线：`Content` 不得回巢、全限定写法零残留、
Handler 必须弱引用、三个定时器不得退回 Handler 延迟消息、`DisplayStats` 线程必须
保留（它要在 display 线程卡死时仍然出日志），外加「管理器非空行 < 1100」。

下一步：批 3 下半 —— `setContent` 的合并窗口（250 ms 最小间隔 + 被替换帧必须
recycle）、`MSG_STOP`/`shutdown` 的 cancel + NonCancellable、剩下三个刷新限速

## 五、风险与回滚

- 每批一个独立提交，批内不改两件事。
- **不做运行时开关（新旧双路径）**：两套刷新路径比一套烂路径更难查，回滚靠 `git revert`。
- 唯一必须小心的是 #9：`setContent` 的 250 ms 最小间隔与「被替换帧必须 recycle」是现在防止点显器闪烁和 Node 泄漏的两条命门，迁移时先写测试再改实现。
- 迁移完成后 `DisplayManager.kt` 预期减少 150–250 行（Handler 消息常量、`Message` 分支、`HandlerThread` 生命周期样板），`@Volatile` 从 20 降到约 6。
