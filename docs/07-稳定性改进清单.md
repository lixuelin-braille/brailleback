## 🔴 S0：native 库 16KB page 对齐（本次最重要发现，已修复）

### 风险

Android 15+ 起支持 **16KB page size**。若 native 库的 `LOAD` 段按 **4KB** 对齐，
在 16KB page 的设备上**加载会直接失败**（`UnsatisfiedLinkError` 或启动崩溃）。

本项目最近一次提交是「HID 输出修复与 **Android 15/16** 协议完善」——
也就是说目标平台正是受影响的版本，而 `libbrlttywrap.so` 是**点显器连接的核心库**。

### 实测证据

用 NDK 的 `llvm-readelf -l` 读 `LOAD` 段的 `Align` 字段：

| 库 | 架构 | 修复前 | 修复后 |
|:---|:---|:---:|:---:|
| `libbrlttywrap.so` | arm64-v8a | `0x1000` ❌ | `0x4000` ✅ |
| `libbrlttywrap.so` | armeabi-v7a | `0x1000` ❌ | `0x4000` ✅ |
| `liblouiswrap.so` | arm64-v8a | `0x4000` ✅ | `0x4000` ✅ |
| `liblouiswrap.so` | armeabi-v7a | `0x1000` ❌ | `0x4000` ✅ |

> `0x4000` = 16384 = 16KB；`0x1000` = 4096 = 4KB。

**4 个库里 3 个不合格。** 而且只有 `louiswrap` 的 arm64 是好的——
说明 8/25 那次重编只处理了它，其余被漏掉了。

### 根因

`service/jni/brlttywrapper/Android.mk:54` 用的是**覆盖赋值**：

```makefile
LOCAL_LDFLAGS := -no-canonical-prefixes -Wl,--allow-multiple-definition
```

这行把构建系统的默认链接参数（含 16KB 对齐）挤掉了。
`louiswrap` 那边的 `LOCAL_LDFLAGS := $(LIBLOUIS_LDFLAGS)` 展开为空，反而没触发这个问题。

### 修复（2 行）

```makefile
# service/jni/brlttywrapper/Android.mk:54
LOCAL_LDFLAGS := -no-canonical-prefixes -Wl,--allow-multiple-definition -Wl,-z,max-page-size=16384

# service/jni/liblouiswrapper/Android.mk:25
LOCAL_LDFLAGS := $(LIBLOUIS_LDFLAGS) -Wl,-z,max-page-size=16384
```

### 重编命令

```bash

NDK_BUILD=C:/tools/android-sdk/ndk/28.2.13676358/ndk-build.cmd
"$NDK_BUILD" APP_ABI=arm64-v8a   NDK_OUT=jni/obj NDK_LIBS_OUT=jniLibs -j4
"$NDK_BUILD" APP_ABI=armeabi-v7a NDK_OUT=jni/obj NDK_LIBS_OUT=jniLibs -j4
```

### 验证（三项都做了）

1. **对齐**：四库 `Align` 全部 `0x4000` ✅
2. **符号完整性**（防 `UnsatisfiedLinkError`）：用 `llvm-nm -D` 对比新旧库导出的 `Java_*` 函数
   - `brlttywrap`：12 个 → 12 个，**完全一致，零缺失** ✅
   - `louiswrap`：5 个 → 5 个，一致 ✅
3. **APK 内核验**：解压 APK 后复查，`lib/` 下四个库均为 `0x4000` ✅

## ❌ S3：native 内存未释放 —— 决定不做

原描述：`TranslatorService.onDestroy()` 是空的，只有一行
`// TODO: Deallocate native data`，liblouis 表缓存不释放。

**审查后认为不值得做，三个理由：**

**1. JNI 层自己的 `malloc` 全部成对 `free`，没有每次调用的泄漏。**
逐行核对 `LibLouisWrapper.c`：
- `translateNative`：`outbuf` / `inputpos` / `outputpos` 都在 `freebufs:`(151-154) 释放 ✅
- `backTranslateNative`：`inbuf` / `outbuf` 在 `freebufs:`(225-226) 释放 ✅

**2. liblouis 的表缓存是「复用型」缓存，不会累积。**
重复 `lou_getTable()` 同一张表会命中缓存、不会重复分配。
所以它不是"每次泄漏一点"，而是"常驻一份"。

**3. 释放的代价高于收益。**
服务销毁后释放掉，下次服务重启要**重新编译整张盲文表**（CPU 开销明显）；
而进程被系统回收时这些内存本来就会全部释放。属于**用启动速度换几 MB 常驻内存**，不划算。

> 结论：真要动 `.so`，也应该为了**修缺陷**（如 C1）而不是为了这个。

## ✅ C1：JNI 在 OOM 后继续用 NULL 指针（C 层真实缺陷，已修复）

`service/jni/liblouiswrapper/LibLouisWrapper.c`

**第 93-95 行**（`translateNative`）：

```c
outbuf   = realloc(outbuf, sizeof(jchar) * outlen);
inputpos = realloc(inputpos, sizeof(int) * outlen);
if (outbuf == NULL || outputpos == NULL || inputpos == NULL) {
    (*env)->ThrowNew(env, class_OutOfMemoryError, NULL);
}                                   // ← 没有 goto freebufs
int result = lou_translate(..., outbuf, ..., outputpos, inputpos, ...);
```

`ThrowNew` 只是**挂起**一个 Java 异常，C 代码会继续往下跑。
于是 `lou_translate()` 收到 NULL 指针 → **段错误**，把"OOM"变成了"崩溃"。

**第 196-198 行**（`backTranslateNative`）有同样的问题。

### 改法

```c
if (outbuf == NULL || outputpos == NULL || inputpos == NULL) {
    (*env)->ThrowNew(env, class_OutOfMemoryError, NULL);
    goto freebufs;                  // ← 补这一行
}
```

### 修复记录（2026-09-03，提交 `e6b10ba`）

原计划是"等真机验证通过后下次重编顺手带上"。实际执行时改用了比原方案**更严**的写法：

```c
// translateNative
jchar* new_outbuf = realloc(outbuf, sizeof(jchar) * outlen);
int* new_inputpos = realloc(inputpos, sizeof(int) * outlen);
if (new_outbuf == NULL || outputpos == NULL || new_inputpos == NULL) {
  free(new_outbuf);
  free(new_inputpos);
  (*env)->ThrowNew(env, class_OutOfMemoryError, NULL);
  goto freebufs;
}
outbuf = new_outbuf;
inputpos = new_inputpos;
```

**为什么不直接用文档原先建议的"补一行 `goto freebufs`"**：那样虽然避免了 NULL 传参，
但 `outbuf = realloc(outbuf, ...)` 在失败时已经把原指针**覆盖成 NULL**，
原内存块再也找不回来 → `freebufs` 只能 `free(NULL)`，原块泄漏。
用临时指针接收则保留原指针，**既避免段错误，也能正确释放原块**。
`backTranslateNative` 同法处理（它只有 `outbuf` 一个 realloc）。

## ✅ S1：`FeedbackManager` 从未关闭（已修复）

`BrailleBackService.shutdownDependencies()` 关了 displayManager /
translatorManager / focusTracker / labelManager / packageReceiver，
**唯独漏了 feedbackManager**，第 633 行还挂着 TODO。
而 `FeedbackManager.shutdown()` 早就在 `FeedbackManager.kt:83` 实现好了，只是没人调。

**改法**：补上 `feedbackManager.shutdown()`。

> **故意没有置 null**：`feedbackManager` 被 `onConnectionStateChanged`、
> `onMappedInputEvent`、`performVolumeAction` 等多处回调引用，
> 置 null 是**拿 NPE 换泄漏**。而 `shutdown()` 本身已释放资源，不划算。

## ✅ S2：`HidBridge` 静态引用不清理（已修复）

`BrailleBackService:419` 只 `set` 不 `clear`；`DisplayService:196` 只清 listener 不清 controller。

后果比泄漏更麻烦：服务销毁后 `isAvailable()` 仍返回 `true`，
于是拿**陈旧的 controller** 去连接（`DisplayService:382/399`）→ 连不上或状态错乱，且现象极难归因。

**改法**：`onDestroy()` 里加 `HidBridge.setController(null);`

> **位置很重要**：必须放在 `shutdownDependencies()` **之前**。
> 否则关闭过程中 `DisplayService` 仍能看到"可用"的 controller 并拿它重连。

## ✅ S4：位置映射 `-1` 未防护（已修复）

`textToDisplayPosition()` 可能返回 `-1`（源码注释自己写着 "May return -1?"），
调用处 `DisplayManager:1267` 直接拿它做减法 → 算出负数/垃圾值往下传。

**改了 3 处（比原计划多 1 处）：**

1. `newDisplayStart` / `oldDisplayStart` 任一 `< 0` → 跳过该节点
   原 TODO 写的是 `return -1`，我改用 `continue`：
   循环里跳过映射失败的节点去试下一个，结果只会更好或相等
   （全失败时仍会落到末尾的 `return -1`），**严格不劣于原方案**。

2. **额外发现的同类隐患**（原清单没有）：
   第 1246-1249 行 `displayToTextPosition()` 在 `displayPos == cursorPos` 时
   直接返回传入的 `cursorPosition`，而调用处传的就是 `-1`；
   于是 `oldTextStart` / `oldTextEnd` 也可能是 `-1`，
   却直接喂给了 `getSpans(-1, ...)` 去查非法区间。已一并补防护。

3. 兜底分支的 `-1` 传递路径同步加了判断。
