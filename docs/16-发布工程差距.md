# 16 - 发布工程差距

体检结论里唯一还称得上「老项目」的一项：**release 构建用 debug 签名、targetSdk 落后于设备**。
这份文档记录实测现状、已经做掉的部分、以及剩下必须人工决定或真机验证的部分。

## 一、现状（2026-11-15 实测）

| 项 | 现状 |
|:--|:--|
| release 签名 | `signingConfig signingConfigs.debug`，`keytool -printcert` 显示 `CN=Android Debug` |
| 仓库内密钥 | **一个都没有**（无 `keystore.properties`、无 `*.jks`） |
| release 产物 | `assembleRelease` 成功，`brailleback-release.apk` **17.72 MB**（debug 33.41 MB，R8 + shrinkResources 生效） |
| targetSdk | 全部 11 个模块都是 **35**；设备已是 Android 17 |
| 前台服务 | `foregroundServiceType="connectedDevice"` + `FOREGROUND_SERVICE_CONNECTED_DEVICE` 权限**已正确声明**（targetSdk 34+ 的硬性要求已满足） |
| 边到边 / insets | 全仓 **零** `enableEdgeToEdge` / `WindowInsets` / `statusBarsPadding` |
| 预测性返回 | 无 `enableOnBackInvokedCallback`、无 `onBackPressed` 处理 |
| 版本号 | 来自根 `gradle.properties`（`appVersionCode=34`），由 `VersionCatalogTest` 门禁守住 |

## 二、已经做掉的（本文件同批提交）

1. **`brailleback/build.gradle` 接入正式签名，且「不配密钥也能打包」**：

   ```groovy
   def keystorePropertiesFile = rootProject.file('keystore.properties')
   def hasReleaseKey = keystorePropertiesFile.exists()
   // ...
   release {
       signingConfig hasReleaseKey ? signingConfigs.release : signingConfigs.debug
   }
   ```

   有 `keystore.properties` 就用它；没有就沿用 debug 签名，行为与之前完全一致 ——
   这样 CI、本机、别人 clone 下来都不会因为缺密钥而红。

2. **`.gitignore` 补上 `keystore.properties` / `*.jks` / `*.keystore`**，密钥永不入库。

3. **CI 注释里的过期数字改准**：`41 套件 / 448 用例` → `49 套件 / 507 用例`。

## 三、使用正式签名要做的（需要你决定密钥身份）

```properties
# 仓库根 keystore.properties（不入库）
storeFile=brailleback-release.jks
storePassword=……
keyAlias=brailleback
keyPassword=……
```

一次性生成：

```powershell
& 'C:\tools\jdk-21.0.12.1+1\bin\keytool.exe' -genkeypair -v `
  -keystore 'D:\软件\brailleback盲文\brailleback-release.jks' `
  -alias brailleback -keyalg RSA -keysize 4096 -validity 36500 `
  -dname 'CN=brailleback, OU=blind, O=lixuelin-braille, C=CN'
```

**这一步必须你自己确认**：签名密钥是长期身份，一旦用它发版，以后升级必须用同一把钥匙，
丢了就无法覆盖安装（只能换包名）。另外不能把 debug 签名的 APK 与正式签名的 APK 互相覆盖安装
—— 换签名前要先卸载，卸载会带走 `/sdcard` 之外的应用私有数据（点显器配置、偏好项都在里面）。

## 四、targetSdk 35 → 36 的真实阻塞项

升到 36（Android 16）之前，这三项必须在代码里解决，而且都要真机看：

1. **边到边强制生效**。targetSdk 36 的应用不再能用 `windowOptOutEdgeToEdgeEnforcement` 退出。
   当前代码里没有任何 insets 处理 —— 设置页、教程页的内容会顶到状态栏下、压到导航条上。
   Compose 侧需要 `Scaffold` + `contentWindowInsets` 或 `Modifier.safeDrawingPadding()`，
   `OverlayDisplay` 这类全屏浮层要单独判断。
2. **预测性返回默认开启**。现有 Activity 没有 `enableOnBackInvokedCallback`，
   返回手势的系统动画会作用在未适配的页面上。
3. **行为变更核对**：`connectedDevice` 类型的前台服务不受 dataSync 超时限制（已确认），
   其余（隐式广播、存储、媒体）本项目不涉及。

结论：**现在不该盲目升 36**。先做 insets，再升，一轮一验。

## 六、release 装机验证（2026-11-15 实测，已完成）

这一项以前写的是「没有装机验证」。现在跑过了，证据链如下。

**验证方式**：release 与 debug 同为 debug keystore，直接 `install -r` 覆盖真机
（`Redmi 24117RK2CC` / Android 17 / API 37），保留应用数据。为了看到服务端行为，
临时把 `BrailleBackService` 追加进 `settings secure enabled_accessibility_services`，
取完日志后**立即恢复原清单**（原值是 MIUI 增强 + SoundBack + TalkBack 三项，未新增 brailleback）。
最后已把 debug 包装回。

**结果**：
