## 1. 问题与根因

**现象**：用户必须先去系统蓝牙设置里把点显器配对好，回到 App 设备列表才认得到这台设备；App 内没有「发现未配对设备并发起配对」的前半段。

**根因**：候选列表只来自已配对集合。`DeviceFinder.findDevices()` 遍历的是 `adapter.bondedDevices`：

- `service/.../display/DeviceFinder.kt:172` — `fun findDevices()`
- `DeviceFinder.kt:184` — `val bondedDevices = adapter.bondedDevices`

未配对设备根本进不了候选，列表里自然看不到。

**后半段本来就是通的**：配对完成后的自动连接路径早已存在。广播接收器把 `ACTION_BOND_STATE_CHANGED` 交给 `connectFromBroadcastIntent()`（`service/.../display/DisplayService.kt:187-189`），其 `BOND_BONDED` 分支在 `DisplayService.kt:1222-1246`：校验是已知设备后摘除未配对候选（`:1233-1237`）、写入 `mPendingBluetoothAddress`、复位旧的 HID 失败标记，再走 `autoConnectBraille()`。本次改动没有另造连接路径，只补上「发现 → 配对」的前半段。

## 2. 一处纠偏：复用既有经典发现机制，不是新加扫描器

早期一版判断曾认为「全项目没有扫描能力」。**这是错的**：经典蓝牙发现早已在用，`adapter.startDiscovery()` 就在 `DisplayServiceConnectionFlow.kt`：

- `service/.../display/DisplayServiceConnectionFlow.kt:482` — `startDiscoveryInternal(reason)`
- `DisplayServiceConnectionFlow.kt:500` — `if (adapter.startDiscovery()) { ... }`

本次新增的是「用户主动发现窗口」与未配对候选收集，**扫描电台本身复用这条既有机制**，没有引入第二个扫描器。

**为什么必须走 BR/EDR 经典发现，而不是 `BluetoothLeScanner`**：TSM 3647 这类点显器只暴露 SPP 串口服务（UUID `00001101`，见 `DeviceFinder.kt:359` 的 `SERIAL_BOARD_UUID`），属经典蓝牙 BR/EDR 设备，不走 GATT。`BluetoothLeScanner` 只扫 BLE 广播包，在这种设备上是错工具——既收不到 SPP 设备，也无法为它发起经典配对。

## 3. 设计：发现窗口来源与候选组装

### 3.1 窗口来源互斥与让位

经典蓝牙同一时刻只能跑一次 inquiry，用户主动查找与连接失败后的自动重连共用同一个电台，必须能区分是谁开的窗。`DiscoverySource` 三态（`service/.../display/DiscoveryWindowTracker.kt:23-32`）：

| 来源 | 含义 | 时长 |
|:---|:---|:---|
| `NONE` | 没有窗口在跑 | — |
| `AUTO_RECONNECT` | 连接失败 / 客户端注册后的自动重连窗口 | 既有 `DISCOVERY_SESSION_DURATION` |
| `USER_DISCOVERY` | 用户在列表页点「查找点显器」打开的一次性窗口 | 12 秒，`DisplayServiceConnectionFlow.kt:37` `USER_DISCOVERY_WINDOW_DURATION = 12000L` |

让位规则（纯状态机 `DiscoveryWindowTracker`，不碰 Android 框架类）：

- 用户窗口抢占电台：先收掉既有自动窗口，再开用户窗口（`DisplayServiceConnectionFlow.kt:449-451`）。
- 自动窗口不得接管或延长用户窗口：`startAuto()` 在用户窗口有效期内返回 false（`DiscoveryWindowTracker.kt:75-82`）；自动窗口延长也只作用于自动窗口（`:85-91`）。
- 窗口到期 / 被取消 / 蓝牙关闭 / 扫描权限被撤，`finishUserDiscovery()` 收窗并把最终列表推给 UI（`DisplayServiceConnectionFlow.kt:473-480`）。

用户主动窗口的准入条件 `shouldStartUserDiscovery()`（`DisplayServiceConnectionFlow.kt:408-429`）：未连接、有客户端、数据文件已解压、屏幕亮、蓝牙开、有扫描权限；与自动重连不同，**不要求自动连接开关打开**——用户主动点查找必须被尊重，即使他关掉了自动连接。

### 3.2 未配对候选如何进入列表

- 窗口内收到 `ACTION_FOUND`：`handleDiscoveredDevice()` 分流（`DisplayServiceConnectionFlow.kt:531-582`）。用户窗口内，只收「非 BONDED 且名称命中名称表」的设备（`:557-563`）；既有自动重连路径仍只认已配对已知设备（`:566-581`），语义不变。
- 名称匹配走纯函数 `DeviceFinder.matchesKnownName()`（`DeviceFinder.kt:319-327`）：先查手写 `SUPPORTED_DEVICES`，再查 brltty 名称表；「TSM」前缀命中 `sk` 驱动条目（`DeviceFinder.kt:827-837`，正则 `Pattern.compile("TSM")` 在 `:837`）。
- 候选按地址去重，名称迟到时刷新（`addUnpairedCandidate()`，`DisplayServiceConnectionFlow.kt:589-606`）。

### 3.3 列表组装顺序

`DeviceListBroadcaster.sendDeviceList()`（`service/.../display/DeviceListBroadcaster.kt:33-79`）：

1. 已配对设备来自 `findDevices()` 的原始顺序，状态码 `BONDED`（`:44-60`）；
2. 本轮发现的未配对设备只追加在后，跳过已在已配对列表里的地址（`:61-70`）。

既有元素的顺序、`LAST_CONNECTED_DEVICE_KEY`（`DeviceFinder.kt:361`）置顶逻辑一字未动。

## 4. 配对状态机

### 4.1 状态与迁移

`PairingStateMachine`（`service/.../display/PairingStateMachine.kt`），纯状态机、不依赖 `android.bluetooth`，可直接 JVM 单测：

```
IDLE → BONDING → BONDED
                → FAILED   （被拒绝 / 启动失败 / 权限不足），可重试
                → TIMEOUT  （超过自设截止时间），可重试
```

- 状态枚举 `IDLE / BONDING / BONDED / FAILED / TIMEOUT`：`PairingStateMachine.kt:19-34`；失败原因码 `NONE / REJECTED / TIMEOUT / COULD_NOT_START / PERMISSION`：`:37-52`。
- 可重试判定 `retryable`：仅 `FAILED / TIMEOUT`（`:81-83`）；再次点配对可从失败 / 超时重回 `BONDING`（`:90-105`）。
- 用户拒绝：`BONDING` 状态下收到 `BOND_NONE` 落 `FAILED / REJECTED`；空闲态的 `NONE` 不动（`onBondState()`，`:123-142`，拒绝分支 `:129-135`）。
- 超时兜底：仍在 `BONDING` 且过截止时间落 `TIMEOUT`（`onTimeout()`，`:145-150`）。

### 4.2 编排落点

`PairingController`（`service/.../display/PairingController.kt`）：

- `PAIRING_TIMEOUT_MILLIS = 60_000L` — `:28`，60 秒超时兜底。
- `handlePairDevice(address)` — `:45`：已配对直接交回既有连接路径（`:69-74`）；同一地址正在配对则忽略重复点击（`:77-82`）；`createBond()` 返回 false 落 `COULD_NOT_START`（`:91-109`）；抛 `SecurityException` 落 `PERMISSION`（`:93-99`）。
- `handlePairingTimeout()` — `:114`。
- `candidateStateFor(address)` — `:123`：把状态机当前态映射成列表状态码；地址不属于当前配对流程时一律 `UNPAIRED`。

Handler 投递：`DisplayServiceHandler.kt:200`（`startUserDiscovery`）、`:214`（`pairDevice`）、`:218`（`schedulePairingTimeout`）；消息分发在 `:320 / :323 / :326 / :329`。

### 4.3 配对成功后交回既有路径

`BOND_BONDED` 后不另造连接：沿用 `connectFromBroadcastIntent()` → `autoConnectBraille()`（见第 1 节），状态机在 `BONDED` 态由该路径继续。

**系统配对确认框由 system uid 弹出，第三方 App 关不掉，也不要去反射或绕过它。** 本项目只调 `BluetoothDevice.createBond()`，等系统广播结果；60 秒超时是兜底，不是替用户点确认。

## 5. 权限与系统限制

### 5.1 清单声明（`brailleback/src/main/AndroidManifest.xml`）

| 权限 | 声明 | 说明 |
|:---|:---|:---|
| `BLUETOOTH` | `:37`，`maxSdkVersion=30` | 仅 API ≤ 30 的旧路径 |
| `BLUETOOTH_ADMIN` | `:38`，`maxSdkVersion=30` | 仅 API ≤ 30 的旧路径 |
| `BLUETOOTH_CONNECT` | `:44` | 枚举已配对设备、读配对状态、`createBond()` |
| `BLUETOOTH_SCAN` | `:45-47`，`usesPermissionFlags="neverForLocation"` | 短窗口发现；扫描结果从不用于推导位置 |

`neverForLocation` 的理由：扫描结果只用于匹配点显器名称表与地址，不进定位链路；声明该 flag 后系统不把本次扫描当作位置来源使用。

### 5.2 运行时申请与被拒降级

- 运行时申请在 `DeviceConnectionComposeActivity.requestBluetoothPermissions()`（`brailleback/.../compose/DeviceConnectionComposeActivity.kt:269-293`）：API 31+ 补齐缺失的 `CONNECT` / `SCAN`；结果回调在 `:75-82`，`CONNECT` 到手即 `poll()` 重扫一次。
- 权限态本地快照 `refreshPermissionState()`（`:225-229`）；查找入口闸门 `DeviceConnectionLogic.canStartDiscovery()`（`DeviceConnectionLogic.kt:108`）。
- **被拒降级**：缺 `SCAN` 时不弹扫描，界面降级为提示用户去系统蓝牙设置配对。文案 `compose_settings_discover_denied`：「缺少蓝牙扫描权限，请在系统蓝牙设置中配对设备」（`brailleback/src/main/res/values-zh-rCN/strings.xml:352`）。

### 5.3 已知系统限制（如实记录，不要假装不存在）

**MIUI / 国产 ROM 后台、息屏扫描受限**：息屏或后台时 `startDiscovery()` 可能被系统直接拦下，或立刻回传 `ACTION_DISCOVERY_FINISHED`。此时本轮窗口在截止时间前收尾，界面表现为「本轮没有发现设备」（代码注释见 `DisplayServiceConnectionFlow.kt:438-441`）。降级路径：引导用户到系统蓝牙设置里完成配对；不要在后台反复重开扫描。权限自检与厂商后台限制的既有盘点见 [17-保活与权限适配](./17-保活与权限适配.md)。

## 9. 手工验证步骤

### 路线 A：未配对 TSM 3647（新链路）

1. 在系统蓝牙设置里解绑（取消配对）TSM 3647，设备保持开机、可被发现。
2. 打开 BrailleBack 设置 → **设备与连接**。
3. 点「查找点显器」。预期：朗读「正在查找附近的点显器……」；约 12 秒一轮。
4. 列表出现 TSM 3647，状态标签朗读「未配对，点显器」，动作为「双击配对」。
5. 双击该候选发起配对。预期：状态变为「正在配对，点显器」，动作标签为空（重复点击被忽略）。
6. 系统弹出配对确认框（system uid 弹出，App 无法代确认）；在框内确认。
7. 配对成功后预期：候选从未配对列表摘除，设备按既有路径自动连接，连接状态播报已连接。
8. 反向验证：在系统框里拒绝配对 → 候选回到「配对失败，可重试」，动作变为「双击重试配对」。

### 路线 B：已配对 Orbit wujie 30（回归链路）

1. 打开 BrailleBack 设置 → 设备与连接。
2. 预期：wujie 30 出现在已配对分区，顺序与最近连接置顶与改动前一致；状态「已配对，点显器」，动作「双击连接」。
3. 双击连接。预期：仍走既有方式直连，连接成功；GATT 旁路未被触发（真机 Entries=0）。

## 10. 已知限制

- **必须经系统配对框**：配对确认由系统 UI 完成，App 不能自动确认、不能绕过；60 秒未完成按超时落可重试态。
- **MIUI / 国产 ROM 后台与息屏扫描受限**：后台 / 息屏可能扫不到设备；降级路径是引导用户去系统蓝牙设置配对（第 5.3 节）。
- **本次未覆盖的场景**：同时多台未配对候选的排序与配对切换；配对成功后首次连接失败的重试归属（走自动重连还是用户窗口，未单独切分）；名称迟迟不回传（`name == null`）时的显示与重试；除简体中文外的语言文案未翻译。
