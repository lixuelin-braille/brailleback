## 作用域与延迟清单（五节）

### ① 作用域：创建者 / 取消点 / 是否等待

- **创建者**：`mainScope = CoroutineScope(SupervisorJob() + Dispatchers.Main.immediate)` 仍由主桥接创建并持有，不随协作类外拆。
- **取消点**：`shutdown()` 首句 `mainScope.cancel()`，把在排的播报延迟与直通区延迟一并撤掉。
- **是否等待**：**无 `join`**。取消后不挂起等待子作业收尾；TTS 与反馈控制器随后由各自的 `shutdown()` 释放。
- 线程：作用域调度器为 `Dispatchers.Main.immediate`，与基线一致。

### ② 三种延迟

| 延迟 | 触发位置 | 句柄归属 | 随作用域取消？ |
|:---|:---|:---|:---|
| 公告播报延迟 | `speak()` 走外部读屏公告分支、`delayMs > 0`：`mainScope.launch { delay(delayMs); announce() }` | `mainScope` 子作业 | 是，`mainScope.cancel()` 一并撤掉 |
| TTS 播报延迟 | `speak()` 走自带 TTS 分支、`delayMs > 0`：`mainScope.launch { delay(delayMs); speech.speakNow(...) }` | `mainScope` 子作业 | 是，随作用域取消 |
| 直通区落地延迟 | `applyTouchExplorationPassthrough()`：`PASSTHROUGH_APPLY_DELAY_MS = 150L`（等 `setServiceInfo` 在系统侧生效） | **独立** `passthroughApplyJob: Job?` | 否，单独 cancel；重设前先 `passthroughApplyJob?.cancel()` 撤上一拍，清理时再 cancel 并置 null |

### ③ 晚到防护（逐条）

| 防护点 | 做法 |
|:---|:---|
| 作用域已取消 | 延迟作业挂在 `mainScope` 下，`shutdown()` 先 `mainScope.cancel()`；取消后在排的 delay 不再投递 |
| TTS 判空 | `speakNow` / `interrupt` / `shutdown` 均先取本地 `val tts = textToSpeech`，`null` 直接返回；`ttsReady` 未就绪时入队（队列上限 8），不往已释放引擎说话 |
| 公告判空 + catch | `sendAnnouncementEvent`：空文本返回 false；`AccessibilityManager` 取空或未启用返回 false；整段 `try/catch (t: Throwable)` 记日志后返回 false |
| 直通区延迟③标志守卫 + 句柄 cancel + catch | 落地协程先判 `!passthrough.isActive()` 即 `return@launch`；重设/清理前单独 cancel `passthroughApplyJob`；`applyRegion`/`clearRegion`/`setTouchExplorationRequested` 各自 `try/catch (t: Throwable)` |
| inactivated 本地判空 | `onBrailleImeInactivated` 先取本地 `val ime = brailleImeForTalkBack`，`null` 不回调 `onTalkBackSuspended()` |

### ④ 创建顺序与取消顺序

- **创建**：字段装配 `speech` → `nodeActions` → `passthrough`；`init { speech.initTts() }` 启动 TTS 引擎初始化。
- **取消（`shutdown()` 内顺序）**：`mainScope.cancel()` → `speech.shutdown()` → `feedbackController.shutdown()`。
- **外部兜底**：宿主在服务销毁/异常时先 `forceClearPassthrough()`（直通区仍活跃则清 Region、撤标志位），再走 `shutdown()`，避免直通区残留导致读屏整屏失效。

### ⑤ 切缝与切后一致性

- 协作类构造参数只传它需要的依赖：`BrailleImeHostSpeech(context)`、`BrailleImeHostNodeActions(service, focusFinder)`、`BrailleImeHostPassthrough(service)`；主桥接持有三个实例，方法调用按原成员名接线。
- 线程模型、队列长度（待播 ≤ 8）、降级口径（TTS 不可用静默降级、公告投递失败回落 TTS）、日志 tag 与基线一致；未新增 public API。

## 源码等价性复核证据

- **方法级比对**：逐方法对照基线 `3ff9ebe` 的 `BrailleImeHostBridge.kt` 与拆后主桥接 + 三个协作类。**17 / 18 个搬迁方法体 `IDENTICAL`**（含缩进与注释）。
- **唯一差异**：`obtainDisplayRegion` 把基线里的 `getWindowManager()` 换成协作类私有 `windowManager()`；两者是同一表达式 `service.getSystemService(Context.WINDOW_SERVICE) as WindowManager`，等价。基线 `getWindowManager()` 本就是该表达式的接口覆写，拆分后窗口管理器取值下沉到 `Passthrough` 内部。
- **内联块**：4 段内联 `object :` / 匿名回调块逐行一致，未改队列与监听口径。
- **主桥接保留方法 diff**：仅委托前缀（`speech.` / `nodeActions.` / `passthrough.`）与标志位访问方式（协作类内 `active` 经 `isActive()`/`setActive()` 暴露）；无方法体重写。

## 为什么这么切

三条数据流各自内聚、不交叉持有可变状态：语音闭环只碰 TTS 引擎与公告事件；节点动作闭环只碰聚焦节点与 `FocusFinder`；直通区闭环只碰服务标志位与系统 Region。作用域、延迟句柄与动作路由留在主桥接，避免取消顺序被拆散。

## 调用方怎么接

- `BrailleIME`（输入法主类）经 `Host` 接口取桥接实例的方式不变；`getBrailleImeForTalkBackProvider`、`setBrailleImeForTalkBack`、`performAction` 等对外方法名与签名不变。
- 协作类为同包 `internal class`，不暴露到模块外；主桥接内部调用按 `speech.` / `nodeActions.` / `passthrough.` 委托。
- 外部兜底清理入口 `forceClearPassthrough()` 名字与语义不变。
