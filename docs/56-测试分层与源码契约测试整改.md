## 二、现状：两类测试混在同一个 `testDebugUnitTest` 任务里

真实测试目录只有五个：`addon/braillecommon/src/test`、`addon/brailleime/src/test`、
`brailleback/src/test`、`brailleback/src/androidTest`、`service/src/test`。

- **行为测试**：构造输入 → 调真实类/纯函数 → 断言输出。例如
  `RefreshGateTest.kt`、`RefreshPolicyTest.kt`、`DisplayTimersTest.kt`（`runTest` +
  `advanceTimeBy`，`DisplayTimersTest.kt:26/:48/:60/:80`）、`VolumeKeyGesturePolicyTest.kt`、
  `BrailleKeyMapPolicyTest.kt`、`ConnectionProtocolPolicyTest.kt`、`UsbHidDevicePolicyTest.kt`，
  以及 service 的 Java 单测 `BondedDeviceFilterTest.java`、`HidConnectionLifecycleTest.java` 等。
- **源码契约测试**：`java.io.File` 定位源码 → `readText()` 读成字符串 →
  `contains(...)` / `Regex.findAll(...).count()` / `indexOf` 先后比较做断言。
  它们不加载被测类，编译通过与否、运行时行为如何，都不在断言范围内。

两类共用同一个 JVM sourceSet、同一个 Gradle 任务、同一道 CI 门禁，报表里无法区分
「行为被钉住了」还是「源码长得跟上次一样」。

## 三、逐个体检（25 个契约测试 + 1 个未命名契约）

归类口径：**A** = 纯源码文本断言，行为失真风险高；**B** = 混合，含真实常量/真实目录数据比对；
**C** = 资源/打包/ABI/构建护栏，约束的本来就是架构而非行为，建议保留但分层。
「代表断言行」均为断言实际所在行（`assertTrue/assertFalse/assertEquals` 或其包裹的 `indexOf`/正则行）。

## 四、为什么危险：盲用户视角的两个方向

### 4.1 假绿：行为已经坏了，测试还是绿灯

这类测试只看「源码里有没有这行字、这个签名、这个顺序」，不执行它。只要坏改动
保留了原字符串和原结构，测试照样通过。对盲用户，下面这些故障没有任何可读提示，
只能在点显器/读屏上直接感受：

- 点显器少刷一帧、重复帧没去掉、空帧把屏幕清了；
- 蓝牙断连后 Wujie BLE 被跳过、落到不响应的 HID 路径，只能重新配对；
- 长按/双击音量键意外调了系统音量；
- 设置页某一项念不出选中状态、整行被拆成两个焦点。

**典型例 1（去重/限速，`DisplayRefreshThrottleContractTest.kt:136-145`）**：断言源码里
`if (refreshGate.isDuplicateOfLast(fingerprint))` 这一行出现在 `translateCurrentContent()`
之前。如果去重判定被改成走另一个 helper、或条件结果被忽略，只要这行字符串还在文件里，
测试就绿；而重复帧照整屏重算，点显器按帧闪烁。

**典型例 2（Wujie 传输顺序，`WujieAutoConnectContractTest.kt:81-87`）**：用
`indexOf("connectWujie(") < indexOf("tryConnectHid(")` 固定顺序。把两个调用挪进策略对象、
或在分支里调换先后，源码字符串的出现次序一变测试才红；但真正决定「先试 BLE 还是先试 HID」
的运行时分支如果写反，只要两处调用文字都在，测试仍然绿。

**典型例 3（音量键隔离，`VolumeKeyIsolationContractTest.kt:115-118`）**：断言长按
runnable 函数体里不含 `adjustSystemVolume(`。若长按动作内部经 `performVolumeAction`
在某条分支上调到音量，源码字符串缺席照样成立；用户听到的是长按音量键直接改了系统音量。

### 4.2 假红：行为完全正确，只是改名/抽组件/换实现，测试先红

反过来，这类测试把内部实现细节钉成了发布条件。一次无害甚至有益的重构——私有函数改名、
行抽成组件、常量提取到 catalog、依赖升到已验证的新版本——都会让测试失败，迫使开发者
要么改测试迁就字符串、要么不敢动老代码。盲文链路里那些最难读的老类（`DisplayService`、
`BrailleBackService`、`DisplayManager`）因此长期得不到重构。

**典型例 4（源码片段耦合 Compose 结构，`BrailleDisplayContractTest.kt:69-75`）**：断言
`BrailleDisplayScreen.kt` 的某段源码里依次出现五个 `item(key = BrailleDisplayLogic.KEY_...)`。
把某一行抽到共享组件、或换一个等价的 `when` 分支写法，行为没变，测试先红。

**典型例 5（版本钉字面量，`DependencyCatalogContractTest.kt:130-137`、
`ComposeMigrationContractTest.kt:66`）**：测试目录里 `compose = "1.12.1"`、
`agp = "9.2.0"` 等字面量。一次经过验证的依赖升级（行为测试全绿）会先被这条契约拦红，
必须同步改测试字符串才能过门禁。

**典型例 6（行数预算，`DisplayServiceSplitContractTest.kt:47`、
`DefaultNavigationModeSplitContractTest.kt:48`、`DisplaySplitContractTest.kt:111`）**：
非空行数上限是拆分当时的余量，与运行时质量无关；合理新增少量逻辑也会先撞行数红线，
倒逼为了过测试而硬拆。

### 4.3 小结

源码契约只能回答「文件长得跟上次一样吗」，回答不了「点显器动对了吗、读屏念对了吗」。
它适合钉外部 ABI、资源清单、打包产物这些**本来就不该随重构改变**的东西；不适合钉
内部行为与实现结构。

## 五、分层方案

### 5.1 三层模型

| 层 | 放什么 | 怎么跑 | 门禁地位 |
|---|---|---|---|
| **L1 行为测试** | 纯函数/策略/目录数据/组件语义的输入→输出断言；androidTest 组件与冒烟 | `src/test`（JVM，含 `runTest` 虚拟时间）+ `src/androidTest` | 唯一阻断行为回归的门禁，CI 必跑 |

| **L3 结构/风格护栏** | 文件行数预算、函数搬迁归属、裸 Handler/旧 Result API/旧限定写法扫描、禁用 `internal` 互调 | 优先 detekt/lint 自定义规则；放不下的进 `archTest` sourceSet | 不阻断合并，作为提示或单独 nightly；行数类只报警不挡门禁 |

### 5.3 目录、sourceSet 与任务拆分建议

- 新 sourceSet `src/contractTest/kotlin`（L2）与 `src/archTest/kotlin`（L3）；Gradle 任务
  `:brailleback:contractTest`、`:service:contractTest` 独立于 `testDebugUnitTest`。
- 过渡期若不动 sourceSet：在测试类上加 JUnit `@Category(Contract::class)` / `@Category(Arch::class)`，
  任务用 `--tests` 或标签过滤分别出报表；CI 行为门禁只跑 L1。
- 命名：L1 保留 `*Test.kt`；L2 用 `*ContractTest.kt`；L3 用 `*ArchCheck.kt`，避免再出现
  `VersionCatalogTest` 这种「行为测试命名、契约测试内容」的混淆。
- 规则化优先：能写成 detekt/lint 规则的（旧 API 缺席、裸 Handler、旧限定写法、`internal` 互调）
  不留在测试里；detekt 接入方式见 [21-静态检查与协程升级](./21-静态检查与协程升级.md)。

### 5.4 怎样保证「改坏行为的提交一定红」

1. 行为判定必须落在可纯 JVM 驱动的对象上：路由选择、目标判定、限速去重、目录分组、
   键位映射先抽成无 Android 依赖的策略/纯函数（现有 `ConnectionProtocolPolicyTest`、
   `RefreshPolicyTest`、`VolumeKeyGesturePolicyTest` 已是先例）。
2. L1 断言输入输出，不断言源码长什么样：给策略喂构造好的状态，断言选择结果/帧计数/
   回调值；时序类用 `runTest` + `advanceTimeBy`（参照 `DisplayTimersTest.kt:26/:48/:60/:80`）。
3. 组件语义由 Compose 测试在渲染后的语义树上断言 `Role`/`stateDescription`/
   `mergeDescendants`，而不是匹配源码字符串（底座见 [39](./39-Compose组件级交互测试.md)）。
4. CI 行为门禁同时跑 `:brailleback:testDebugUnitTest` 与 `:service:testDebugUnitTest`；
   L2/L3 单独 job 出报表，失败不混在行为红里。
5. 每个转层的契约用一条变异对照确认：故意改错行为（调换分支、删掉去重、改反条件），
   新 L1 用例必须红；改名/抽组件/升版本后 L1 保持绿。

## 七、成本与是否阻塞发布

成本口径：**S** ≤1 天；**M** 2–4 天；**L** 1–2 周。

| 项 | 成本 | 阻塞发布？ | 说明 |
|---|:--:|:--:|---|
| 契约/行为测试打标签或拆 sourceSet，报表分开 | S | 否 | 纯组织调整，不改断言强度 |
| CI `unit-tests` job 补跑 `:service:testDebugUnitTest` 并汇总其 XML | S | 否（但应尽快做） | 当前 service 行为单测与契约都只在本地跑，CI 红灯覆盖不到 service 回归 |
| `DependencyCatalogContractTest`、`NativeBridgeContractTest`、`TableArchiveContractTest`、`VersionCatalogTest` 归 L2 | S | 否 | 本就是外部约束，分层后单独报表 |
| `CoroutineScopeContractTest`、`LegacyResultApiContractTest` 的扫描项转 detekt/lint 规则 | L | 否 | 规则编写与基线冻结见 [21](./21-静态检查与协程升级.md) |
| 限速/去重/空帧/回收转虚拟时间行为测试（`DisplayRefreshThrottleContractTest` 拆分） | M | **是**（盲文输出链路缺口） | 点显器闪烁/清屏是盲用户直接可感故障，L1 补齐前发版需人工真机验收限速四项（[21](./21-静态检查与协程升级.md) 第 107-115 行已列未验项） |
| Wujie/USB 路由判定转纯状态机行为测试（`WujieAutoConnectContractTest`、`UsbHidWiredContractTest` 拆分） | M | **是**（断连恢复链路缺口） | 传输顺序与回退条件当前只有源码顺序断言 |
| 音量键隔离装配侧 fake 依赖行为测试（`VolumeKeyIsolationContractTest` 拆分） | M | 建议是 | 误调系统音量是可感知故障；策略层已有 `VolumeKeyGesturePolicyTest` |
| Compose 屏幕语义转语义树断言（四个大屏契约 + `ComposeMigrationContractTest`） | M | 部分是 | 朗读合并/选中状态相关断言缺失影响读屏可用性；组件底座已有 [39](./39-Compose组件级交互测试.md) 五例可扩 |
| 键位分发、设置目录、跨进程名单改运行期读真实常量/数据类 | M | 否（资源一致性留 L2 兜底） | 消除正则解析源码的假红面 |
| 连接编排状态机行为化（fake 蓝牙/USB/HID 后端，覆盖断连→重连→回退） | L | **是**（断连恢复链路缺口） | 现有 Java 单测覆盖编解码与设备过滤，未覆盖连接编排时序 |
| 保活不断、朗读语义、机型兼容落仪器测试或手动验收脚本 | L | **是**（三条链路真机缺口） | 需设备在手；模拟器 x86_64 跑不了 native（[19](./19-仪器测试.md) 第 151-159 行） |
| 行数预算/函数搬迁类 L3 护栏 | S（降级） | 否 | 改为报警提示，不挡合并；不为过测试硬拆 |
